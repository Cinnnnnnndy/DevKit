TUI 的关键特征

TUI 能做、CLI 做不到的

全屏布局——多面板并排、独立滚动、焦点切换，不只是向下追加文本

实时刷新——局部重绘，500ms 级更新周期，数据变了画面就变

交互状态——选中、展开、排序、筛选、模态对话框——CLI 只能用管道 | less 凑

色彩与密度——24-bit 真彩、braille 8× 亚字符精度、块字符渐变

TUI 能做、GUI 做不到的

SSH 直达——不需要 X11 转发、VNC、远程桌面，一条 SSH 就是完整体验

零依赖——不需要显示服务器、窗口管理器、GPU 驱动，headless 服务器直接跑

带宽极低——传输的是字符差分，不是像素帧，高延迟网络下依然流畅

可脚本化——终端天然支持 tmux 录制、expect 自动化、管道衔接

TUI 不是 CLI 的美化版，也不是 GUI 的降级版。它是一种独立的交互范式：在终端的字符网格内构建完整的应用体验——有布局、有状态、有实时、有交互。CLI 太轻（无布局、无状态），GUI 太重（需要窗口系统、无法 SSH 直用）。TUI 恰好站在"服务器上做工程"这个场景的最优点上。
常见误解纠正：① "TUI 就是带颜色的 CLI"——错，CLI 没有布局和事件循环，TUI 有。② "TUI 是简陋的 GUI"——错，TUI 不依赖显示服务器，能在纯 SSH 下提供完整体验，这是 GUI 做不到的。③ "TUI 过时了"——错，lazygit、k9s、btop 等现代 TUI 工具正在快速增长，因为云原生与远程开发场景天然需要终端内的完整体验。

IDE 插件方案：本地装 IDE → 挂远程开发 → 文件同步 → 再连回服务器

              零同步、零延迟、与被观测对象同机

只有原生 TUI 才成立的四件事

① 与被观测对象同机——性能剖析、进程表、NUMA 拓扑、驱动状态必须在目标机采集

② SSH 即完整体验——本地零安装，服务器上一个二进制

③ 自主渲染权——braille、真彩热力需直接控制终端缓冲

④ 常驻状态——上下文水位、索引、实时曲线需要进程活着

由此产生的设计约束

键盘优先鼠标可选——SSH 常无鼠标，每个鼠标操作必须有键盘等价

不假设 IDE 存在——跳源码要内置预览，不能只给深链接

低带宽友好——局部刷新而非全屏重绘，采样率可降档

终端能力协商——真彩/braille/鼠标运行时探测并降级

单二进制交付——无外部依赖

本地与远程是同一个二进制、同一套体验。上图是生产场景（工程师 ssh 到鲲鹏机器干活）；但同一个 devkitai 也直接跑在本地开发机上做交叉编译迁移，不连任何远端、零配置启动——Demo 演示的正是这条本地路径。两种部署共用同一份渲染、同一套快捷键、同一个会话模型，差别只是被观测对象在本机还是在远端。这种"一个二进制两处都完整"恰恰是原生 TUI 独有的：CLI 两处都能跑但没有工作台，IDE 插件两处都别扭（本地要装 IDE、远程要挂远程开发）。
三种形态并存而非替代：CLI 留给 CI/脚本；IDE 插件留给本地轻量编码；原生 TUI 面向"在服务器上做迁移、诊断、调优"这个 DevKit 真正的主战场。三者共用同一套 Agent Runtime 与 MCP 工具，差异只在壳。

设计系统继承：Web → TUI

直接继承设计系统的 token 体系与设计原则。但 Web 与终端的表达能力差异巨大——本节的核心工作是把 Web 端 token 翻译成终端可实现的 TUI token，而不是简单复制色值。

3 级阴影✗ 无阴影改用边框强度 + 表面步进表达层级

继承的第一性原则（原样保留）：中性表面承载布局，强调色传递语义 · 不在 UI 面板背景使用大面积饱和填充 · 高亮色阶仅用于数据可视化 · 每个表面只选一种强调机制，不叠加多种视觉技巧 · 动效只服务于功能，无装饰性循环动画。

品牌色替换带来的两条硬约束。DevKit 品牌色 #0077FF 取代原本的 #4369EF 后，实测出两个必须处理的问题：

① 对比度不足，文本不能直接用品牌色。#0077FF 在 #101010 上对比度 4.61:1（勉强过 AA），但在 #1C1C1C 表面上降到 4.12:1，不达 AA 标准。规范：品牌色只用于填充、边框、焦点底色；一切文本/链接/图标用 --primary-hover #3D98FF（各表面上 5.8–6.5:1，全部达标）。这与设计系统原色不同——旧的 #4369EF 更暗，反而是靠 hover 档提亮；新品牌色更亮更饱和，问题变成了"纯色在深灰表面上灰度差不够"。

② 与 data-viz 的 copy-blue 撞色。品牌色色相 212°，设计系统的 copy-blue 色阶色相 219°——只差 7°，在终端里（无法靠尺寸/位置区分）用户无法分辨"这条泳道是 CPU"还是"这条泳道被选中了"。解决方案见下。
域色映射 — 蓝色专属品牌，数据色从非蓝取

既然品牌蓝会出现在色块上（进度条、选中底色、焦点），copy-blue 必须退出 TUI 的数据可视化色板。全产品建立一套固定的域色映射，同一个观测对象在任何页面都是同一个色相：

三条贯穿全族的规则

① 八分之一格精度是地基。垂直方向有 ▁▂▃▄▅▆▇█，水平方向同样有一套 ▏▎▍▌▋▊▉█。一个 10 格宽的 bar 因此能表达 80 档而不是 10 档——没有它，82% 和 85% 画出来一模一样，而「兼容性 82%」这种数字恰恰是拿来做判断的。

② 并置的图必须共用量程。多列条形、多系列折线、Before/After、双向面积——分别归一化会让每条都填满画布，看着都一样忙。而并置的全部意义就是比较。

③ 画不下的东西要显式说，不能悄悄省略。排行榜尾部标 … N more，火焰图标 N 帧过窄未显示。悄悄丢掉窄帧会让「我看全了」变成一个错觉，这比不画更危险。同理也不做「最小宽度 1 格」的兜底——那会让窄帧集体虚胖、把宽帧挤走，图就假了。

Metric Bar 的着色 —— 一处规范冲突，已按本文档解
COMPONENT.md v0.2 原写「阈值着色：<60% accent · 60–85% warn · >85% error」，即把语义色刷到 bar 上。但本页 Colors 一节定死语义色只上字符与短文本、永不上色块。冲突按本文档解：
元素走什么色因为它是
bar 本身域色阶顺序取档数据
数值文字 / 前缀符号阈值语义色结论

这不是折中。一个 90% 的 CPU 利用率本身不是错误——只有当它被判定为问题时才该出现语义色。把两者刷成一个颜色，等于宣布「数值大 = 出事了」，而这在性能调优场景里恰恰经常是反的：利用率高往往是好事。

对齐 —— 禁用裸 ljust / rjust

所有图元的标签与表格列必须走 render/text.py 的 fit() / pad() / truncate()。Python 数的是码位，终端排的是单元格，一个汉字占 2 格：f"{'折线':<12}" 实际占 14 格，f"{'Sparkline':<12}" 占 12 格——同一张表里两种标签混用，列就是歪的。这类 bug 只在中文标签下出现，纯英文界面上怎么测都测不出来，所以靠纪律不靠自觉。

为什么用 <pre> 而不是截图。SVG 按「一个字符 = 一个单元格」推进 x 坐标，浏览器里 CJK 字形的实际步进由字体定，于是中文标注全叠在一起。改成 <pre> 由浏览器自己排字，代价是标签列一律 ASCII、中文只许行尾——这条在生成期由断言把着，违反直接报错。

Components

图元尺寸与排布

上一节定了每种图长什么样，这一节定每种图多大才该画。起因是多图元同屏：一屏上同时挂着 braille 曲线、热力网格、gauge、双向面积、算子表、Trace 泳道，每种图的尺寸若各自临时定，结果就是没人知道某张图在一条 24 列的栏里到底该画还是不该画——「画得下」和「读得出」不是一回事。判决集中在 app/devkitai/layout.py 的纯函数里，不由各个 widget 自己拍。

最小可读尺寸

低于它这张图就不该画，该退成 fallback 那一列写的形态。不是「缩着画」。

推荐尺寸

给得起就给到这个数。多数图元吃到推荐值即停，不摊成长条。

纵横比约束

列÷行的允许区间。越界不是拒画，是把盒子裁到带内再画。

收缩优先级

同屏并置、空间不够时谁先让。按降级损失排，不按重要性排。

格子不是像素 —— 视觉纵横比 = 列 ÷ (2 × 行)

终端字符格的宽高比约 1:2，所以下表里所有比例都是列÷行的原始格子比，换算成眼睛看到的比例要再除以 2。一张 40 列 × 6 行的折线，格子比 6.7，视觉上是 3.3:1 的横长条——按格子数直觉去想比例，会稳定地想扁一倍。

这些数不取 4 的倍数。页面 CSS 的 --grid-unit:4px / --chart-trim 管的是这张网页自身的排版；图元尺寸的单位是字符格，每个数都由图元自己的几何定死——像素数字的 11 列是「3 位 × 3 列 + 2 个间隔」，braille 曲线的 3 行是「12 个点阵行」。把它们凑成 12 和 4 就是把规格编出来，两套网格不该互相对齐。

收缩优先级 —— 按降级损失排，不按重要性排

同屏并置、空间不够时谁先让？答案不是「谁不重要谁让」，而是谁掉一层损失小谁先让。这跟整屏降级里「Console 先让、Canvas 后让」是同一条原则——过程信息让位给结论。同一档内先让推荐面积大的：从大图上收回一样多的格子，代价更小。

档让出的代价图元
① 先让掉成一行数字，结论零损失像素数字 · 分段 · 数图 Stat · 进度 · 水位 · Metric Bar · Sparkline
②掉一层仍在回答同一个问题面积 · 双向面积 · 多列条形 · Before/After
③压缩会丢掉比较能力排行 · 散点 · 折线
④ 最后让形状即信息，压扁等于没画火焰图 · 泳道 Timeline · 热力网格

① 档那七种为什么最先让，一句话：Metric Bar 掉成 84.3% 什么都没丢，像素数字掉成常规数字丢的只是「一眼可见」。④ 档相反——火焰图深度方向不做降采样（§3.7），压扁了栈形就没了；泳道少一行就少一条「谁在等谁」的线索。

和整屏降级链对上 —— 这一节是 FRAMEWORK.md §8 的图元级对应

整屏降级链决定给几个 Canvas、每个多宽；这一节决定每个 Canvas 里那张图怎么缩。两者必须对得上，否则会出现「整屏还在给栏，图元级已经全线拒绝画」的空栏。所以两套判决放在同一个模块、由同一份单测同时压。Canvas 外尺寸减去左右框线与内边距（各 2 列）才是图元可用宽；行方向只减上下框线，标题排在上框线里不另占行。

实现

规格与判决都在 app/devkitai/layout.py：PRIMITIVES 是十七种画法的规格表，chart_box() 把 Canvas 外尺寸换算成图元可用盒子，fit_box() 给出「在这个盒子里实际该画多大」——返回 None 就是「不该画，走 fallback」，shrink_order() 给同屏收缩顺序。跟 resolve_layout() 一样是纯函数，因为这类逻辑平时不会有人手动把终端拖到 97 列去验，不测就等于没写。app/tests/test_layout.py 里压了这些：规格自洽（自己在自己声明的尺寸上得画得下）· 判决永不超出给定盒子 · 低于最小尺寸必须返回「不画」· 三条硬约束各自的失真 · 六档整屏里每一档都容得下全部 ① 档图元 · 全宽度扫描 40–400 列不许出现「什么图都画不了」的空栏。

设计系统分割方法在 TUI 的四条落地规则

① 嵌套用表面层，不用阴影

外层 background → 面板 surface-1 → 面板内表头/工具条 surface-2 → hover surface-3 → 选中 surface-4。最多嵌两层，第三层改用留白分隔而非再加一层底色。

② 层级用边框强度

同级区域分隔 border-subtle；跨职责区域（Console 与 Canvas 之间）border-default；当前焦点区域整圈升到 border-strong。焦点不靠颜色靠边框强度 + 左侧 ▮ 标记。

③ 圆角只给浮层

框架内所有固定区域用直角 ┌┐└┘（radius-sm/md）；只有浮层、模态、Palette 用圆角 ╭╮╰╯（radius-lg）。圆角在这套体系里等于"浮起"，不能随便用。

④ 留白只取六档

面板内边距 space-4（左右 2 列 / 上下 1 行）；面板之间 space-5（3 列）；大区块 space-6。禁止裸数字 padding——这是设计系统"不使用任意像素值"在 TUI 的对应物。

Demo 故事线

一条连续叙事，供演示串讲。主角：性能工程师，要把一套 x86 上的 nginx 迁到鲲鹏 ARM64 并调到可上线的性能。全程在本地开发机上跑，不连任何远端服务器——打开终端就能开始。

演示环境：纯本地，零前置。Runtime 随二进制本地起，不需要填服务器地址、不需要凭据、不需要网络。devkitai 一敲就进工作台——这是演示的第一个说服点，也是"原生 TUI 单二进制交付"的直接兑现。
幕发生什么观众看到的"哇点"
① 开场本地终端敲 devkitai，全屏工作台直接起来，零配置、零登录。首屏显示环境已就绪 + 检测到 3 项能力未装，一键装好。一条命令进工作台——不用装 IDE、不用配环境、不用连远端
② 提需求直接说"把 ./nginx 迁到鲲鹏"。系统不立刻动手，先出 5 步 Plan 并标注要调哪些工具。AI 先给计划再执行，计划可改
③ 补配置执行到"编译验证"时停下：本地没探测到 aarch64 交叉编译工具链，需要指定路径和输出目录。就地弹层收集（带 Tab 路径补全），填完接着原来那一步继续。不是一开始灌一堆表单，要用到才问，且说明为什么要
④ 出报告兼容性 82%，2 个 Critical、8 个 Warning、21 个可自动修。文件风险热力一眼定位到 crypto.c。热力图定位问题文件
⑤ 审改动逐个看 patch：_mm_pause() → asm("yield")，附知识库案例编号和 ARM 手册章节。每条改动都有证据可溯源
⑥ 编译翻车Build 失败。系统不只报错，直接转入诊断：根因链路图指到内存对齐，置信度 91%，给修复方案。修完重编，PASS。失败是分支不是死路——就地转诊断
⑦ 看性能下一步引导给了三条建议，选"跑性能基线"。Trace 出来：HBM 持续饱和而 NPU 有气泡 → memory-bound。并置才看得出的结论，AI 直接标在图上
⑧ 调参数参数优化给三套方案对比表（QPS / P99 / CPU / 内存），推荐方案 A：worker 数对齐 64 物理核 + NUMA 亲和绑定。应用后 QPS 42k → 61k。方案对比而非单一建议，改动都带"为什么"
⑨ 场景化引导进入场景化调优：选"高并发短连接"profile，再针对性调一轮。调优不是一次性的，按业务场景分档
⑩ 收尾Session Summary：21 修复 / 2 待人工 / Build PASS / QPS +45%。导出报告。全程可追溯，一份报告交差
串讲节奏建议：①–② 讲"为什么是 TUI"（2 分钟）· ③–⑥ 讲"AI 怎么把活干完且可审计"（5 分钟，⑥ 编译翻车是全场最关键的一幕，它证明系统能处理不顺利的情况）· ⑦–⑨ 讲"可观测与调优深度"（5 分钟）· ⑩ 收。总时长 12–15 分钟。
