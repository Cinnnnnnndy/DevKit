为什么必须重取证据

AI Agent TUI 这一层三个月翻一次。举一个可核对的例子：Claude Code 在 2026-07-14 到 08-20 的 37 天里发了 20 多个带 TUI 行为变更的版本（2.1.208 → 2.1.237），涉及输入高亮偏移、全屏重绘、权限对话框文案、markdown 缩进、emoji 截断……

结论是：任何超过半年的 AI TUI 交互结论都要重新验证。本部分的取证窗口固定为 2026-06-01 → 2026-08-20。

证据规则
版本号 + 日期是硬要求。正文中每条产品行为都尽量带 v2.1.235 · 8/18 这样的出处；拿不到版本号的写「文档态」，拿不到日期的标 ⚠️ 待核查。
一手 > 二手。官方 changelog、官方文档、仓库 README 为一手；技术媒体与聚合站为二手，仅用于「存在性」而不用于「细节」。二手来源在表格中以 〔二手〕 标注。
行为差异优先于功能罗列。「有没有 @ 引用」没有信息量，「@ 补全在多行输入里高亮偏移一格、8/18 才修」才有。
Bug 与其说明书同等重要。一条被修掉的渲染 bug，等于一条被公开的实现约束——我们照抄约束比照抄功能安全。
一处口径澄清：需求里的「harness」在 2026 年有两个所指——① 泛指Agent 脚手架层（组装上下文 → 调模型 → 解析回复 → 派发工具）；② 特指以此自我标榜的一类产品，代表是 Grok Build（SpaceXAI，2026-07 开源，自称 "coding agent harness and TUI"）与 Pi。本报告两个都收：把 harness 作为一条产品线（F2 收 Grok Build 与 Pi），同时把「harness 化」当作一种架构趋势来分析（F11 leader 模式、F7 ACP）。

交互设计动作项 · 七层栈 → 组件契约
组件边界输入框实现必须按层拆分模块：paste-decoder / key-decoder / width-measurer 三个必须是独立、可单测的纯函数，禁止合并进「输入框组件」内部私有逻辑——F8 的 measure≠render 事故正是合并的后果

验收顺序验收输入框时从 L1 往上验：先证明宽度测量与截断在 CJK/emoji/Nerd Font 混排下不漏，再验协议协商，再验粘贴通道，最后才验补全与语义——顺序反过来会把地基问题误判为「个别 case」
L2 键盘协议层 · 三条硬事实

协议要主动协商

pi-tui 启动时就去协商 Kitty 键盘协议，目的很具体：分清 Esc 与 Alt+x 序列，并拿到 key-release 事件（复杂组合键必需）。

来源：pi-tui README

Ctrl+J 是个雷

开了 extended key reporting 的终端上，Ctrl+J 在 agent view 的输入里插不进换行——Claude Code 2.1.212 · 7/17 修了一次，2.1.229 · 8/12 又修一次，第二次顺手把换行快捷键补进了 ? 帮助面板。

修 bug 的同时补可发现性——这个动作值得抄。

复制键也归协议管

Claude Code 全屏模式下 Ctrl+Shift+C 复制；仅在支持 Kitty 键盘协议的终端（kitty / WezTerm / Ghostty / iTerm2）上 Cmd+C 才可用。

同一功能在不同终端有不同键 = 提示文案必须按能力动态变。

FLOOR 04 · 交互域 02

配置方法 · 四种哲学，且它们互不兼容

这一层没有共识，只有四种立场。选哪种不是口味问题——它直接决定「用户改一个键位要付出多少认知成本」和「我们能不能把配置讲清楚」。

① 声明式命名空间Codex
TOML · 可版本化 · 可 diff

全部塞进 ~/.codex/config.toml 的 [tui] 段，结构极其规整：

# keymap 按 7 个 context 分层
[tui.keymap.global]
clear_context = "ctrl-shift-l"
[tui.keymap.composer]
submit       = ["enter", "ctrl-m"]
history_prev = "ctrl-p"
open_external_editor = []   # 空数组 = 解绑

# 状态栏 = 有序数组，不是布尔开关
tui.status_line = ["model", "approval", "context_usage"]
tui.terminal_title = ["spinner", "project"]
tui.theme = "dracula"

三个设计决定值得抄：① keymap 按 context 分层（global / chat / composer / editor / pager / list / approval），具体覆盖全局；② 解绑用空数组，不用魔法值；③ 状态栏与终端标题都是「有序数组」——用户决定显示什么、按什么顺序。

〔二手〕[tui] 细节；命名空间自 v0.128.0 起

② Schema 化分家opencode
JSON + Schema · UI 与 Runtime 分离

把「界面配置」和「运行时配置」拆成两个文件：tui.json（主题 / 键位 / 滚动 / 光标 / 鼠标 / 通知）与 opencode.json（服务端与运行时）。tui.json 带 $schema 指向 opencode.ai/tui.json，编辑器直接有补全和校验。

键位可设 "none" 或 false 禁用；leader_timeout、scroll_speed、diff_style（auto/stacked）、鼠标捕获开关都在这里。

这条分家是对的。换终端要改的只有 tui.json，换模型/服务端要改的只有 opencode.json——DevKit 有本地终端 / SSH / 低能力终端三套场景，这个切分能省掉大量解释成本。

③ 对话内改配置Claude Code
/config 对话框 · 不用离开会话

三条路径并行：settings.json、环境变量、会话内 /config 对话框。本窗口最大的变化是把「改配置」从「停下来」变成「顺手」：

④ 可解释性优先Grok Build
grok inspect · 配置来源可追溯

配置本身平淡（~/.grok/config.toml），但它给了一条别人都没有的命令：grok inspect——在当前目录下列出配置来源、instructions、skills、plugins、hooks 和 MCP servers。

③ 窄屏会吃掉 diff 的语义 CC 2.1.216 · 7/20

① 中断与排队 —— Esc 是本产品最重要的一个键

⑧ 多端与远程 —— TUI 正在与会话解耦

三条独立证据指向同一个方向：Grok Build 的 leader 模式（一个 agent 进程多个客户端，UI 断开会话不死）；Claude Code 的 Remote Control / cloud session（ListAgents 把断开的标为 offline、云会话标为 cloud；/teleport 提示怎么在本地接着干）；Amp 重构 CLI 的目标之一就是可远程控制。

对 DevKit 是刚需，不是加分项。我们的会话跑在鲲鹏服务器上，一次迁移编译可能几十分钟。「关掉本地终端 → 会话继续 → 明天换台机器接回来」是基本诉求。这要求会话状态从第一版起就不绑定在 TUI 进程里——这是架构决定，不是后续可以补的功能。

FLOOR 15

机会点 · 第二部分给 DevKit 的 8 条

按差异化价值 × 实现成本排序。前四条是「行业还没解决、且我们有场景优势」；后四条是「行业已有答案、我们必须一次做对」。 = 差异化价值， = 实现成本。

01

上下文用量归因面板

空白：全行业只显示「用了百分之多少」，没有一个回答「谁在占」。

我们做：把上下文拆成系统提示 / 工程索引 / 已引用文件 / 工具结果 / 压缩摘要五段，用第一部分已有的单色阶条形展示，每段可下钻、可释放（「丢掉这 12 个已读文件」）。DevKit 的上下文里工程索引和编译日志占比极高，这个面板对我们比对通用编码 Agent 更有价值。

02

结果驱动的左树（风险树，不是文件树）

分歧点：AI 派放弃左树、改用 @ 模糊搜索；但模糊搜索要求用户先知道文件名片段——迁移场景不成立。

我们做：左树的节点是风险项 / 待改项 / 编译失败项，选中驱动右侧（照 lazygit），分区可隐藏可重排（照 superfile v1.6.0），默认折叠、一键唤出（把宽度让给对话流）。这是我们与所有 AI Agent TUI 最正当的一处形态差异，理由来自场景而不是审美。

03

缺配置 = 一等公民的暂停-补齐-续跑

空白仍在：第一部分已判定「没有一个产品把缺配置做成一等公民的流程」。本窗口有了最接近的两个零件：Claude Code 的 /permissions 可在工作中打开且立刻对本轮生效，和 /goal 的退避式自动汇报（30min → 1h → 2h）。

我们做：Agent 卡在「缺交叉编译器 / 缺目标机凭据 / 缺性能计数器权限」时，进入显式的 Needs-input 态（照 Claude Code 的 agent view 状态名），给出补齐入口，补齐后从断点续跑而不是重来，长时间未补齐则退避提醒。

04

配置来源可追溯：devkit inspect

来自：Grok Build 的 grok inspect（列出配置来源 / instructions / skills / plugins / hooks / MCP servers）。

为什么对我们更重要：DevKit 装在客户的鲲鹏服务器上，现场排查成本极高，而配置来源有五层。这条实现成本很低、诊断价值极高，建议第一版就有。

05

会话与 TUI 进程解耦（leader 模式）

来自：Grok Build 的 leader 模式、Claude Code 的后台会话与 Remote Control、Amp 的远程可控重构。

为什么是刚需：一次迁移编译几十分钟，用户会关掉本地终端。这是架构决定，第一版不做以后补不上。实现成本高，但必须现在决定。

06

三档字符资产 token（nerdfont / emoji / ascii）

与第一部分的渲染分档（braille / block / tty）同构、共用同一次 capability 探测。硬要求：任何图标都不得承载唯一语义；measure 与 render 共用同一个 display-width 函数（照 pi-tui 的 visibleWidth() / truncateToWidth()）。

07

审查界面绕开一切美化中间层

来自：Claude Code 2.1.222 · 8/4 把 diff 数据源改为 raw git blob、忽略 workspace 配置的 diff driver。

我们的场景更严：迁移会改编译选项、intrinsic、汇编片段——任何「帮你美化过」的 diff 都可能掩盖真实字节差异。同时定死 diff 降级顺序：先丢上下文行 → 再丢语法高亮 → 行号与 ± 号永不丢。

08

把权限 / 计划 / diff 定义成协议数据结构

来自：ACP 的行业化，以及 Grok Build 的那句判断——权限不是 TUI 里的模态 hack，而是协议上可见、任何客户端都能渲染的决策。

我们做：即使第一版只有 TUI，这三类交互的数据结构也独立于渲染层定义。这样以后接 IDE、Web 评审页或 CI 报告时，渲染换掉、语义不动。
