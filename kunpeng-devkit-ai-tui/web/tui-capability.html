CLI / GUI / TUI —— 定义与边界

三个缩写经常被混用，但它们代表三种根本不同的交互模型。理解差异是理解"为什么选 TUI"的前提。

TUI 的关键特征

TUI 能做、CLI 做不到的

全屏布局——多面板并排、独立滚动、焦点切换，不只是向下追加文本

实时刷新——局部重绘，500ms 级更新周期，数据变了画面就变

交互状态——选中、展开、排序、筛选、模态对话框——CLI 只能用管道 | less 凑

色彩与密度——24-bit 真彩、braille 8× 亚字符精度、块字符渐变

TUI 能做、GUI 做不到的

SSH 直达——不需要 X11 转发、VNC、远程桌面，一条 SSH 就是完整体验

零依赖——不需要显示服务器、窗口管理器、GPU 驱动，headless 服务器直接跑

带宽极低——传输的是字符差分，不是像素帧，高延迟网络下依然流畅

可脚本化——终端天然支持 tmux 录制、expect 自动化、管道衔接

TUI 不是 CLI 的美化版，也不是 GUI 的降级版。它是一种独立的交互范式：在终端的字符网格内构建完整的应用体验——有布局、有状态、有实时、有交互。CLI 太轻（无布局、无状态），GUI 太重（需要窗口系统、无法 SSH 直用）。TUI 恰好站在"服务器上做工程"这个场景的最优点上。
常见误解纠正：① "TUI 就是带颜色的 CLI"——错，CLI 没有布局和事件循环，TUI 有。② "TUI 是简陋的 GUI"——错，TUI 不依赖显示服务器，能在纯 SSH 下提供完整体验，这是 GUI 做不到的。③ "TUI 过时了"——错，lazygit、k9s、btop 等现代 TUI 工具正在快速增长，因为云原生与远程开发场景天然需要终端内的完整体验。
TUI Capability · 最需先钉死的一条

产品形态：原生 TUI 应用

这不是命令行工具，不是 IDE 里的终端面板，也不是插件里的聊天框。三者的差别决定了后面所有交互设计的推论。

形态代表运行方式能力边界
CLI 工具devkitai_cli
porting_workflow_cli		一次性进程，执行完退出无状态、无布局、无实时；输出即日志
IDE 插件Cline + DevKit MCP
（手册记载的当前形态）		寄生在 IDE 进程内受宿主 UI 框架约束；渲染由 IDE 决定；必须先有 IDE
原生 TUI 应用本产品独立常驻进程，全屏接管终端，自有事件循环自主布局 / 状态 / 快捷键 / 渲染；直接跑在目标机器上
为什么必须是原生 TUI
DevKit AI 部署在鲲鹏 Linux 服务器（手册确认）：

  工程师笔记本 ──ssh──▸ 鲲鹏服务器（openEuler / 麒麟）
                            │
                            ├─ 待迁移工程源码就在这里
                            ├─ 编译器 / 构建产物就在这里
                            ├─ 性能计数器 / NPU 驱动就在这里
                            └─ DevKit AI 服务 :8000 就在这里

IDE 插件方案：本地装 IDE → 挂远程开发 → 文件同步 → 再连回服务器
              多一层同步与延迟，性能采集尤其失真

原生 TUI 方案：ssh 上去，直接 run，全屏工作台
              零同步、零延迟、与被观测对象同机

只有原生 TUI 才成立的四件事

① 与被观测对象同机——性能剖析、进程表、NUMA 拓扑、驱动状态必须在目标机采集

② SSH 即完整体验——本地零安装，服务器上一个二进制

③ 自主渲染权——braille、真彩热力需直接控制终端缓冲

④ 常驻状态——上下文水位、索引、实时曲线需要进程活着

由此产生的设计约束

键盘优先鼠标可选——SSH 常无鼠标，每个鼠标操作必须有键盘等价

不假设 IDE 存在——跳源码要内置预览，不能只给深链接

低带宽友好——局部刷新而非全屏重绘，采样率可降档

终端能力协商——真彩/braille/鼠标运行时探测并降级

单二进制交付——无外部依赖

本地与远程是同一个二进制、同一套体验。上图是生产场景（工程师 ssh 到鲲鹏机器干活）；但同一个 devkitai 也直接跑在本地开发机上做交叉编译迁移，不连任何远端、零配置启动——Demo 演示的正是这条本地路径。两种部署共用同一份渲染、同一套快捷键、同一个会话模型，差别只是被观测对象在本机还是在远端。这种"一个二进制两处都完整"恰恰是原生 TUI 独有的：CLI 两处都能跑但没有工作台，IDE 插件两处都别扭（本地要装 IDE、远程要挂远程开发）。
三种形态并存而非替代：CLI 留给 CI/脚本；IDE 插件留给本地轻量编码；原生 TUI 面向"在服务器上做迁移、诊断、调优"这个 DevKit 真正的主战场。三者共用同一套 Agent Runtime 与 MCP 工具，差异只在壳。
TUI Capability

TUI ≠ CLI

TUI 拿到的是全屏可寻址缓冲 + 事件循环，能力集远大于 CLI。设计时必须主动消费这些能力，否则做出来的只是带框线的 CLI。

设计准则：每画一个页面先问三个问题——① 这里能不能用 braille 提到 8× 密度？② 这里能不能用颜色承载一个额外维度？③ 这个元素能不能点、能不能滚、能不能拖？三个都答“否”的页面，说明还停在 CLI 思维。

渲染分层 T0–T4

高层必须能向低层降级（SSH 老终端、CI 日志、16 色环境）。每个组件都要声明层级与降级路径。

硬性要求：T4 的每个鼠标操作必须有键盘等价路径（无鼠标的 SSH 是 DevKit 主战场）。T3 在 NO_COLOR / 16 色下自动降级为 T1，语义不能丢。T5 必须永远可降级——它依赖终端支持，不能作为唯一表达路径。

T5 · 终端图形协议 —— 之前被低估的一整层
一个必须纠正的假设：终端不只能画字符。现代终端支持图形协议，可以渲染真正的位图。实拍佐证：euporie 在终端里渲染 matplotlib 图表、LaTeX 公式、HTML/CSS 表格与真实图片；TUI 媒体库渲染电影海报；SimUtil 把手机模拟器画面嵌进面板；甚至有人在终端里跑 Pokemon。这意味着"复杂图表必须简化成字符"这个前提是错的。

Foundation · 最容易做错的一条

Chrome 层 vs Canvas 层 —— 不是所有东西都用字符拼

TUI 常被误解成“全部由 ASCII 拼出来的界面”。不是。现代 TUI 框架（OpenTUI）提供的是真正的 UI 组件系统——有表面层、边框、圆角、状态、图标、徽标、滚动条。字符拼接只是其中一种渲染手段，且只该用在特定地方。

反面案例就在我们自己的稿子里。早期的 Demo 把 Dock、工程树、任务列表全做成了裸文本行——没有选中态的层次、没有 hover、没有图标、没有徽标、缩进靠空格对齐。那不是 TUI，那是把 CLI 输出塞进了一个框里。参照 MobaXterm：它的左侧面板有分组标题、图标、悬停高亮、计数——这些都是 UI 组件该有的东西，TUI 一样做得到。
分界原则：结构用组件，数据用字符

怎么判断一个区域属于哪层
问一句：这块内容是「结构」还是「读数」？

结构 —— 用户在这里做的是选择、导航、切换、确认
        → Chrome 层，用组件。需要状态表达（选中/悬停/焦点）
        例：工程树里选 crypto.c · 任务列表切任务 · Evidence 点开某条

读数 —— 用户在这里做的是看数值、比大小、找异常
        → Canvas 层，用字符。需要密度与对齐
        例：NUMA 热力图 · Trace 泳道 · latency 曲线 · diff 增删行

两者混在一个面板里时，按子区域分别处理：
  Migration Report 面板 = Issue 列表（组件） + 兼容性 bar / 风险热力（字符）
  算子表 = 行选中与排序（组件） + 单元格里的 bar（字符）

为什么这条重要：① 状态表达——字符拼不出 hover/selected 的层次感，而“我现在选中的是哪一项”是工作台的基本诉求；② 自适应——组件能随宽度伸缩截断，字符对齐依赖固定列宽，一变窄就崩；③ 可维护——style props 改一处全局生效，字符拼接每处都要重算列宽（本规范里那些 ASCII 框就是靠脚本算宽度才对齐的，这恰恰说明它不适合做框架）。

反过来，数据区也不能用组件：64 核热力网格如果用 64 个 div，密度、对齐、性能全都做不到——那里就该是字符网格。两层各司其职，边界清晰。

TUI Capability

框架选型

关键前提：DevKit AI 已通过 MCP over streamableHttp（:8000）暴露能力，TUI 本质是客户端。实现语言与 Agent Runtime 解耦，选型可纯按“渲染能力 + 设计系统落地成本 + 团队栈”决策。

已定：TypeScript 5.9 + React 19 + OpenTUI 0.5.1 + Bun。FTXUI 是 C++ 库，与技术栈方向不符，已排除（其 Canvas 双层绘图 API 的分层思路仍值得在自建 braille 封装时借鉴）。Textual（Python）曾作为候选但已排除——OpenTUI 与 OpenCode 同栈，生态复用优势决定性。
维度OpenTUI（TypeScript）★ 已选Textual（Python）· 对照
生态位Zig 编写的原生 TUI 核心 + TypeScript 绑定，另提供 C ABI；OpenCode 生产环境在跑Textualize 出品，基于 Rich，Python TUI 生态最大
样式系统组件式架构 + 灵活布局；样式为 style propsTCSS —— CSS 子集，含变量、选择器、伪类
设计 token 落地React 组件 props + theme context，设计 token 通过 theme provider 注入内置主题系统（predefined themes），变量可直接承载设计 token
内置组件@opentui/core 提供命令式 API 与全部原语；@opentui/react 提供 reconcilerButton / Tree / DataTable / Input / TextArea / Select / Tabs ...
Canvas / 图形核心含缓冲级绘制；@opentui/three 提供 Three.js WebGPU 渲染器Rich 提供渲染原语，braille 画布需薄封装
鼠标 / 动画✓ 主打 correctness / stability / performance✓ 完整鼠标 + animate() 缓动
OpenCode 复用高（同栈）——Agent 流式渲染、工具调用展示、会话管理可直接复用低（可通过 MCP 复用能力，不复用代码）
与 DevKit 生态通过 MCP 客户端对接 DevKit Intelligence；Bun 运行时性能优异Python 贴近 AI / 编译分析 / 数据处理工具链
为什么 OpenTUI 是对的选择——决定性理由是生态复用与渲染能力。OpenTUI 是 OpenCode 的底层引擎，Agent 流式渲染节奏、工具调用展示折叠策略、会话切换与上下文管理的交互实现可以直接复用，不需要从零开始造。React 19 的 reconciler 让组件逻辑与声明式 UI 天然吻合，设计 token 通过 theme provider 注入，Web 端与终端端共用同一份设计语言。

次要理由：@opentui/core 核心含缓冲级绘制能力，braille / 热力等图表原语的底座更坚实；Bun 的启动速度和运行效率在 SSH 低带宽场景下表现优异；TypeScript 的类型系统确保组件契约与设计 token 的类型安全。
OpenTUI 路线要自己补的三块。① Command Palette——需自建模糊搜索命令面板以兑现 P09（Textual 内置此组件，OpenTUI 需要自行实现）。② 热力网格——T3 层的 NUMA 网格、Trace 密度带需自定义 Widget。③ 可拖拽分栏——P23 的布局预设需自建拖拽交互。
