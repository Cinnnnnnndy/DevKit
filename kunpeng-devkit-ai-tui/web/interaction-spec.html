Spec A

A · 模型与 Token 的会话内管理与配置

这一节定义：模型和 token 告警线能在会话里看、也能在会话里改，改完立刻生效、痕迹留在对话流里。权限边界：只看不改（浮层点选不算回执）、改了要留痕、改错了要说明为什么。模型的身份是「别名」（它在哪个端点上由「端点」这一层回答）——同一节里 A2 定命令语法（含模型 ID 重名与未配密钥两种拒绝）、A4 定提示行、A5 定命令候选规格（模型候选浮层本轮删除）、A6 定状态矩阵。

为什么不做右上角浮标：Claude Code 与 opencode 都把这类提示放在 prompt 下方单独一行——和输入内容物理隔离，输入多长都不冲突，窄屏时整行收起也不损失功能。右上角是 Web 的习惯：输入一长必然和正文打架，窄屏时右上角也最先没地方放。所以本轮明确否掉右上角方案（用户最初考虑过），选「输入框下方一行」。
顺序为什么是这五层：从下往上离输入框越远的东西越「可有可无」——调优曲线可以没有（只在 HPO 场景出现），建议操作可以没有（只有结果后有），候选菜单只在打字时出现；只有输入框和提示行始终在。

为什么进对话流而不是 toast：「我什么时候把它改成 85 的」是一个会被追问的问题，答案必须在滚动历史里查得到；toast 三秒后消失，翻历史时它从来没存在过。写入位置在流末尾并自动滚到底，回执只进当前场景的那条流，翻历史不串场。
回执只说业务，不说设计：回执的职责是「这次发生了什么、你该怎么改」，不是解释产品语义。所以 demo 里 /tokens 120 只回「超出可选范围 20–95 · 要关掉提示用 /tokens 95」，不回「告警线是『你想在第几个点被告知』、超过 100% 等于不提醒自己」这类产品语义；同理 /model deepseek-v3-671b 只列候选的别名与端点，不回「换个端点额度与计费也跟着换」这句设计理由。
这些语义与理由归 index.html 的对应单元定义（Checklist Row / Model Switcher / Command Echo 卡里写全），不重复进业务流——demo 复刻的是用户真实使用场景，业务流里只能有业务事实与产品 UI 文案。判断标准：这句话如果换成另一个模型、另一个项目就不成立，它是业务；只跟「本产品怎么设计」有关的，是标注。
两类最容易漏掉的标注，都已按此收回：位置自述——「底栏的 ctx 当前值不变」→「当前用量不变」（数字显示在哪是单元的事，回执只报数字）；行为自述——「其余可直接切」→ 删（候选列表怎么操作属 Model Switcher，不属这次会话的业务状态）。同理，子 Agent 收口语里「你可以在会话列表里点开它、也可以让它单独停下来」也已删除，只留「跑完会自动并入并向你汇报」。
两个入口只留一份痕迹：敲完整命令、从候选菜单选一行，是同一个动作的两个入口，都要写回执；但流内浮层里点一行（Model Switcher）不算——那是同一屏「看现状」段的就地操作，浮层自己的 current 标记就是它的反馈，再写一条回执只会把流撑长。

单 Agent 内工具并发上限4与子 Agent 并发上限同量级，避免一个子 Agent 把整机吃满
资源独占工具全局串行profiler 类（perf_record 等）不并发同机同时采集会互相抢 CPU 与 PMU 计数器，采出来的性能数据是失真的——这是刻意的取舍：并行度换吞吐，但不拿性能数据的可信度去换。这句话只写在这里（规范），不进会话流：换个项目它依然成立，属产品的价值取向；会话里只说这次发生了什么事，见下方受阻说明块
串行时其余工具照常并发串行是按工具类别打的标记，不是整条流水停下来
峰值并发要可读收口区给「14 次工具调用 · 峰值并发 3」并发度是这次编排的成本与收益的解释项，不能只在动画里表现
⚠ 并发采集会互相干扰
sub-1 与 sub-3 都要跑 perf 采样。同机同时采集会互相抢 CPU 与 PMU 计数器，采出来的性能数据是失真的 —— 所以我把 profiler 类工具串起来跑，其余工具照常并行。
说明行只写这次任务的因果，不写产品的价值取向：这一块原来还有第二行「宁可这一轮少一点并行度，也不拿性能数据的可信度去换」，已删——它换个项目依然成立，属规范（上面 B2 那条「资源独占工具全局串行」就是它的落点），在会话里复述一遍等于把规范读给用户听。会话里的受阻块只答「谁在抢什么、我因此改了什么、接下来怎么办」，到了 1–3 行封顶。
为什么用「受阻说明块」而不是折叠日志：这不是错误，也不是日志——它是一条会被用户追问「为什么不能一起跑」的规则。说明块回答「为什么、后果是什么」，日志回答「刚才发生了什么」，两者的读者和寿命都不同。放在编排区顶部，是因为它影响的是整屏的解读（看到两条 profiler 行为什么不并行，答案就在上面一行）。

C2 默认收起规则 —— 判据是「还需不需要你看」，不是深度
卡片状态默认理由
已完成收起（只留头部一行）结论已经在头部摘要里了（收益、耗时、工具数），过程不需要你现在读
进行中展开「现在在干什么」是你要盯的唯一一件事
受阻待裁决展开它需要你现在做决定，收起等于把待办藏起来
已收住（触顶回退）收起已止损，不需要动作；但它不能从树上消失——收起的卡片头部仍写「已收住回退基线」
为什么判据不写成「按深度收起」：如果按深度收，最深的那个受阻项会被父级一起藏掉——而它恰恰是唯一需要人看的东西。反过来，一个已经跑到第 4 层的进行中分支，藏起来也没意义。收不收，只由「还需不需要你看」决定。
可收起 ≠ 只收嵌套的那些：所有卡片都可收起（头部即开关），而不是只给多层嵌套的卡片加收起——同一屏里两种卡片行为不同，用户会先花时间判断「这张能不能点」。
C3 编排泳道 · 槽位 · 隔离
要素规格理由
泳道（Orchestration Lane）同屏并置、对齐同一条时间轴，右端给耗时与状态；main 在最上并发不靠动效表达「同时」——静态帧、SSH、截图里都要读得出来
并发上限4 子 Agent（16 逻辑核）与「单子 Agent 内工具并发上限 4」同源，避免两级并发相乘把机器打满
槽位（Concurrency Slot Gauge）给「还剩几个」而不是「现在几个」；■■■□ 3 / 4会耗尽的是槽位，不是并发数；子级继承父级剩余槽位，不单独开池（否则嵌套会绕过全局上限）
隔离方式每个子 Agent 独立 git worktree，完成后由主 Agent 合并并行的前提是改动不互相踩；合并冲突为 0 是这套编排的验收指标之一
共享只读tiancheng 策略库 20523 案例 · 知识库检索并发读、不排队只读资源不需要串行——把只读也排队是白白浪费并行度
C4 token 归属 —— 父子不双算
规则算法为什么必须这么算
归属每个 Agent 只计自己的调用；父级汇总 = 自身 + 全部后代，按 Agent 去重否则每加一层就重复计一次，越深的编排越显得贵，用户会因此不敢用深编排
算例（单级）main 总计 268.8k = 自身 168k + sub-1 18.4k + sub-2 支 82.4k—
算例（多级）sub-2 小计 82.4k = 自身 41.2k + sub-2.1 9.6k + sub-2.2 21.8k + sub-2.2.1 9.8k已回退的分支（sub-2.3）成本计入发起它那一方的一轮，不再单独成项
呈现头部 Token Badge 就地挂在卡片上；父级汇总额用一行文字说清算法数字要能就地验证——用户会问「你这 268.8k 怎么算的」
并发成本提示「子 Agent 占比 63.7% —— 并行度越高，token 放大越明显，这是并发编排的真实成本」并发不是免费的，成本要显式说出来，而不是藏在总数里

D2 画不下怎么办 —— 显式说画不下
情形处理理由
超过 3 层中间层收成一个可交互的 … 节点，Enter / Space / 点击就地展开，节点文字写明「更深 N 层已折叠」画不下就显式说画不下，不能悄悄吞掉——沿用工程树那条既有决策
深度触顶（第 4 层还想往下）不下钻，收住并回退基线，不留半成品再往下，协调成本与 token 放大盖不住收益；触顶必须是一条有明确终态的规则，不是「跑到超时」
D3 「没做完」的三种样子 —— 必须长得不一样
状态方块含义下一步由谁做
受阻待裁决实心金有问题，需要人来决定人（不静默重试——受阻原因是语义冲突，重试只会重复烧 token）
触顶收住空心金没做，但是主动止损，不是失败无人；已回退到基线
画不下（折叠）无方块有内容，只是屏幕放不下用户点开
三种的区分落在状态方块的填充上：受阻是实心金（还在等你），已收住是空心金（已经停下来了），同一个色相靠填充就分得开，不必再看文字。折叠的 … 不标方块——它不是状态，是「画不下」。三种的中文解释仍由说明列给全（「验证未通过」「触达深度上限，已收住」），颜色只负责说「这里需要你看一眼」。
D4 状态传播 —— 父级不继承子级失败色
规则行为理由
父级不自动失败sub-2.2.1 受阻 → sub-2 仍是「进行中」父级只认自己那一行的事实。一旦继承，越往上颜色越脏，最后 main 永远是红的，颜色就失去了指示作用
受阻必上抛冒泡到 main 的收口清单不能烂在第 4 层没人看见——收口横幅要报出「1 受阻待裁决」
不静默重试受阻项停下等人语义冲突类问题重试只会重复烧 token
本地阻塞不扩散某支文件的改动不与其它支重叠时，其余支可先交付这是并行的意义：不让一个慢支拖住全部
D5 验收条件
  • AC-D14 层嵌套下，深度只用「缩进 + 编号」两个可验证信号；不存在状态导轨或第二套深度色。
  • AC-D2超过 3 层的部分收为 … 节点，节点文字含被折叠的层数，且可键盘展开。
  • AC-D3受阻 / 已收住 / 折叠三种「没做完」在方块填充或无方块上互不相同，且各自有中文解释列。
  • AC-D4子级受阻时父级状态色不变；受阻项出现在 main 收口清单里。
  • AC-D5深度触顶时的文案明确写出「已收住 / 回退基线」，且不存在半成品改动被合入。
  • AC-D6窄屏下缩进不封顶、不换行折断；最坏 64px 缩进时仍能读完目标名。

/model <别名或模型 ID>[model] PRIMARY（写别名）model.entries 里存在这样一条：NAME 或 ID 与之相等，且唯一命中，且该端点的 API_KEY 已配置（PROVIDER = "ollama" 免密钥）新起的子 Agent 继承 · 运行中的不换多义（≥2 条命中）/ 无匹配 / 未配密钥 → 拒绝；多义时列出候选的别名与端点

命令不是配置文件的快捷方式，是它的另一个写入口。两边写的是同一个值，所以在哪边改，另一边马上就是新值——正因为如此，这里不需要「应用」按钮，也不需要「同步」状态。任何形式的「命令改了一份内存状态、配置文件还是旧的」都是缺陷。
为什么配置是「一条 = 一个模型 + 它连的端点」：端点、密钥、额度、计费主体都是端点账号（BASE_URL + API_KEY）的属性，不是模型的属性；同一个模型 ID 可以在多个端点上存在。（本轮改动）所以配置从「供应商 → 模型」两层改成 [model.entries.<key>] 平铺，每条自带 NAME（别名）/ ID / PROVIDER（协议）/ BASE_URL / API_KEY；PRIMARY 与 MODEL_OVERRIDE 一律写别名——别名是唯一的寻址名，重名的那几条才需要和 ID 不同。
与 demo 的差异只有排版：agent-workspace.html 右侧代码列更窄，同一份文件把分组注释单独起了一行、PROVIDERS 折成两行；字段名、值与结构完全一致，对照时以字段为准。

E3 额度与水位（Quota Bar）

额度挂在端点账号上：切端点就换一整套数字与重置语义。共享网关给的是时间窗（5h / 7d），本机推理给的是资源占用（GPU / 队列）——两者不是同一个东西，不该硬凑成同一组标签。读不到额度时（例如没配密钥）不给空条，改一句「为什么读不到」。（本轮改动）分组键从「供应商 id」下沉到端点主机名：它由 BASE_URL 推出来，不是用户要填的第三个字段；用户自己填的端点读不到额度也不算配置错误。

  • AC-E2不存在「应用 / 保存 / 同步」按钮或状态条。
  • AC-E3流内模型卡与管理页列表的模型清单 = model.entries 的并集；改配置文件后两处即时变化。
  • AC-E4subagent.MODEL_OVERRIDE 生效时，卡片头部能看出该子 Agent 用的是哪个模型（可覆盖而不静默），写法为别名。
  • AC-E5「看」与「改」的数字同源：develop:model-token 一屏里的 token / ctx 水位与底栏、提示行三处完全一致（同一个 METRICS 记录、同一个 setModel() 写入口），不存在第二个数据源。
  • AC-E6阈值越界时回执给出可选范围与「正确写法」，且阈值保持不变。
  • AC-E7[model] 段的 PRIMARY / MODEL_OVERRIDE 只接受别名，且该别名必须能在 model.entries 里唯一命中；写了一个对不上任何条目、或对上多条的字符串视为配置错误（不能靠运行时的「猜一个」兜底）。
  • AC-E8额度条、流内模型卡的端点分组、管理页表单三处展示的端点状态与配置一致：未配 API_KEY 的 OpenAI 兼容端点三处都是「可见但不可用」，Ollama 端点不算缺密钥。

F10 唯一事实源，以及本轮的待裁决项
已裁决 · 「供应商」与「Provider」两条轴收敛成一条：Provider 是协议，端点是 Base URL + API Key
裁决依据：「之前和 PRD 冲突的按照 PRD 为准」。旧结构：供应商（devkit-gateway / kunpeng-local / private-cloud）是模型的上层分组，端点、密钥、额度、计费都挂在它身上；命令与配置文件一律写 供应商/模型（§4A / §4E）。
新 PRD：Provider 只有 OpenAI Compatible / Ollama 两个取值，它是协议；端点由 Base URL 承担、账号由 API Key 承担——「供应商」这个中间层在新 PRD 里不存在了。
裁决结果（本轮已执行，不再是"两套并存"）：
① 命令语法去掉 供应商/ 前缀——只有一个写法：别名或模型 ID。重名靠别名消歧（PRD 里本来就有这个字段，默认等于模型 ID，重名的那几条才另起名字）。
② 额度挂到端点：分组键 = 端点主机名（由 BASE_URL 推出来），不再要求用户填「供应商」；PROVIDER_QUOTA 更名 EP_QUOTA。
③ 旧浮层保留，但分组头改成端点：它承担的是「会话内就地切换」这条快路径，与整页管理页职责不重合（快 vs 慢、只选 vs 增删改），因此不退休；它内部写的一直是同一份配置，不构成第二个事实源。
配置文件随之一并改（§4E 已同步）：[model.providers.<id>] 两层结构改成 [model.entries.<key>] 平铺，每条自带 NAME（别名）/ ID / PROVIDER（协议）/ BASE_URL / API_KEY；PRIMARY 与 MODEL_OVERRIDE 写别名。
唯一保留的旧成果：额度条与「未配密钥可见不可选」——PRD 没提额度，但它不构成冲突，只是从「供应商账号」换挂到「端点账号」。自建端点读不到额度时明确说「无额度信息」，不算配置错误。
本轮已经做掉的「唯一事实源」：激活模型只存在一个地方（激活记录的 key），底栏、提示行、侧栏节点、管理页列表的行尾状态词「使用中」、流内模型卡的 current 标记四处都是它的派生显示；任何一条切换路径（模型卡点行 / /model <别名> / 管理页「设为激活」）都写同一个入口。为什么值得单独说：上一版底栏读的是「当前模型」、管理页读的是自己的激活项，两份状态在「删掉激活项」「在页面里激活」「复制一条」这三条路径上必然分叉——分叉之后最难查的不是显示错，而是「同一个设置有两处各写各的」。
startup 页的提示落在哪：PRD 要求「启动页与主页面顶部状态栏高亮提示」。本轮在站点启动页（仓库根 index.html）加的是两个直达入口（?page=model 与 ?scene=develop/no-model），没有加一条「未配置模型」的告警——启动页是文档入口页，在它上面挂产品的运行时状态会读成「这个文档站没配模型」。产品内的缺省态提示已完整落在演示页顶栏胶囊 + 引导卡 + 底栏三处。若需要启动页也出告警 banner，属于产品态与文档态的边界问题。（已按「PRD 优先」向 PRD 靠：“启动页”被解释为产品或 demo 的入口屏——本交付面里没有独立的产品启动页，缺省态因此完整落在演示页顶栏 + 引导卡 + 底栏三处；站点启动页给的是能直达该状态的入口。）
