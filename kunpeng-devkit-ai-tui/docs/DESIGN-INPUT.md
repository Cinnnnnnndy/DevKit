## 1. 项目背景

DevKit AI 是面向鲲鹏开发者的 AI Agent 工具，覆盖**迁移、开发、诊断、调优**四类核心场景。产品以 **TUI（Terminal User Interface）** 为主要交互形态：用户在终端启动 DevKit AI，用自然语言与 Agent 交互，Agent 通过 Skill、Tool、文件系统等能力完成复杂任务。

与传统 CLI 不同，DevKit AI TUI 不只是「在终端输出文字」，而要承担类似 IDE 的**任务组织、状态展示、过程观察和任务控制**能力。

| 形态 | 运行方式 | 能力边界 |
|---|---|---|
| CLI 工具 | 一次性进程，执行完退出 | 无状态、无布局、无实时 |
| IDE 插件 / 内嵌终端 | 寄生在 IDE 进程内 | 受宿主 UI 约束；必须先有 IDE |
| **原生 TUI 应用** | **独立常驻进程，全屏接管终端，自有事件循环** | **自主布局 / 状态 / 快捷键 / 渲染；直接跑在目标机器上** |

选 TUI 的理由是工程现实：DevKit 部署在鲲鹏 Linux 服务器上，待迁移源码、编译器、性能计数器、驱动全在那台机器上。IDE 插件方案要本地装 IDE + 挂远程开发 + 文件同步，多一层延迟，性能采集尤其失真。

因此本次设计的核心不是做一个「终端聊天窗口」，而是建立一套：

> **可接入、可理解、可观察、可控制、可交付的 Agent 工作界面。**

### 1.1 技术约束（设计不得越界）

TypeScript 5.9 · React 19 · `@opentui/core` 0.5.1 · `@opentui/react` 0.5.1 · Bun。
设计每一处都要同时过四关：①产品体验是否成立 ②React + OpenTUI 是否实现得了 ③是否该沉淀为可复用组件 ④宽屏 / 窄屏 / SSH / 低能力终端是否可用。

**实现不了的视觉效果不许留给后续阶段自行解释。** 与技术约束冲突时，记录冲突证据、影响范围和待裁决问题，在裁决前保持 `draft`，不得静默偏离或创造第三套规则。

## 2. 用户

### 2.1 核心用户

鲲鹏开发者 · 软件迁移开发者 · 应用开发者 · 系统运维与诊断人员 · 性能调优人员 · AI / Agent 技术用户 · 熟悉 Linux / Terminal 的极客用户。

### 2.2 能力假设

| 可以假设用户会 | 不可以假设用户会 |
|---|---|
| 用 ssh、看日志、读 diff、跑编译 | 理解 Agent 的内部执行机制（planner / tool loop / context window） |
| 判断一处代码改动对不对 | 知道哪个 Skill 该在什么时候装 |
| 看懂火焰图、热点函数、NUMA 概念 | 记住 Provider / Base URL / API Key 的正确组合形态 |
| 接受键盘优先的操作方式 | 忍受「点了按钮但屏幕没反应」 |

**结论：技术门槛可以高，产品门槛必须低。** 凡是要求用户理解 Agent 实现机制才能操作的界面，都是设计缺陷。

### 2.3 使用环境

本机 Linux / 远程鲲鹏服务器（ssh）/ 开发机 macOS · Windows 终端。
宽度分布是设计变量而不是常量：160 列是理想态，**120 列是主力，80 列必须可用**。

## 3. 场景

### 3.1 业务场景

| 场景 | 用户要什么 | 结果形态 |
|---|---|---|
| 迁移 | 系统迁移 · 应用源码迁移 · 容器迁移 · 数据库 SQL 迁移 | 兼容性报告 + 逐条改动 diff |
| 开发 | 代码开发 · 代码分析 · 代码优化 · 亲和加速库替换 | 代码改动 + 构建验证 |
| 诊断 | 硬件诊断 · 系统问题诊断 · 崩溃与内存定位 | 根因链路 + 修复方案 |
| 调优 | 系统调优 · 参数调优 · 性能分析（热点 / 火焰图 / NUMA） | 方案对比图表 + 前后性能 |

### 3.2 贯穿全流程的三个连接场景

它们不属于任何单一业务场景，却在每个场景里反复出现，因此必须做成系统级机制而不是页面细节：

- **配置补齐**——执行到一半发现缺工具链 / 缺凭据 / 缺参数（P27）
- **下一步引导**——一个阶段结束后给状态相关的建议（P28）
- **多任务管理**——长任务后台跑，用户同时开着几个（P29）

### 3.3 环境接入场景

| 环境 | 判定 | 界面职责 |
|---|---|---|
| 本机即鲲鹏服务器 | 探测 `aarch64` + 鲲鹏标识 | 直接可用，不打扰 |
| 本机 Linux / macOS / Windows，目标在远端 | 架构不匹配 | 给出「连接远程鲲鹏服务器」入口，但**不阻断本地可完成的任务**（源码扫描、静态分析） |
| 远程 ssh 会话 | `SSH_TTY` 存在 | 降低重绘频率、关闭高频动效，宽度按实际 PTY 取 |
| 低能力终端 | 无 truecolor / 无 Braille / `NO_COLOR` | 走渲染降级链，形状承载信息，不依赖色相 |

## 4. 设计目标

六条目标，每条都给出可判定的达成判据。

### 4.1 降低启动门槛

支持：直接启动 TUI · 启动时带 Prompt · 恢复历史 Session · 非交互式 CLI 执行 · 本地环境自动识别 · PC 与远程服务器适配。

```bash
devkitai                                  # 交互式 TUI
devkitai "帮我迁移这个 C++ 项目"           # 启动即执行
devkitai --resume <id>                    # 恢复历史任务
devkitai session list                     # 查看历史 Session
devkitai --non-interactive "检查这个项目"  # CI 可调用
```

> **判据：用户不应该因为环境、连接方式或启动参数而无法开始工作。**

### 4.2 降低模型配置成本

配置链路：`Provider → Base URL → API Key → 获取模型 → 选择模型 → 测试连接 → ✓ Ready`。
必须主动诊断（拉模型列表、鉴权、网络、可用性），并把底层错误翻译成用户语言。

> **判据：用户感觉是在「连接一个可用的 AI」，而不是在配置一堆技术参数。**

### 4.3 让 Agent 的工作过程可观察

用户任何时刻都要能看到：在做什么 · 用什么 Skill · 调什么 Tool · 读写哪些文件 · 到第几步 · 是否需要决策 · 是否异常 · 能否中断。

> **判据：用户永远知道 Agent 在做什么，而不是面对一片等待中的黑屏。**

### 4.4 让执行过程可控制

中断 · 改任务方向 · 回答 Agent 的问题 · 确认高危操作 · 暂停 · 后台运行 · 切换任务 · 恢复任务。

> **判据：Agent 可以自主执行，但用户始终拥有控制权。**

### 4.5 让复杂任务可管理

Session · Agent Title · 多任务 · 后台任务 · 任务状态 · Resume · 任务切换。

> **判据：从「聊天记录管理」升级为「Agent 任务管理」。**

### 4.6 让结果可快速获取

做了什么 · 改了什么 · 解决了什么 · 产生哪些文件 · 是否还有风险 · 下一步做什么。

> **判据：不要让用户从大量 Agent 输出里自己找最终价值。**

## 5. 核心能力

### 5.1 启动与环境接入

首屏必须同时给出：产品标识与版本 · 欢迎语 · 四类能力介绍 · 输入框 · 基础命令 · **当前环境检测结果**。

**不做纯 Logo 开屏。** 首屏要同时回答：环境状态 / 阻塞项 / 输入口 / 可继续的上下文。「最近」和「建议」两行让用户零输入就能往下走——这是常驻进程相对 CLI 的直接兑现，CLI 没有「上次」。

环境检测判定：鲲鹏服务器 · 普通 Linux · Windows · macOS · 远程环境。无法直接完成目标任务时给出明确提示与远程连接入口，例如：

```text
当前环境未检测到鲲鹏服务器，是否连接远程鲲鹏服务器？
```

### 5.2 命令体系

首屏只给常用命令，不一次性铺开：

| 命令 | 作用 |
|---|---|
| `/help` | 命令帮助 |
| `/skill` | 可用 Skill 与安装卸载 |
| `/view-skills` | 浏览 Skill 文件、源码与说明 |
| `/sessions` | 历史任务 |
| `/model` | 选择模型 |
| `/provider` | 配置模型服务商 |
| `/connect-server` | 连接远程服务器 |
| `/info` | 完整能力说明 |

自然语言是第一入口，**命令是等价快捷方式而不是主路径**。发现性靠 `Ctrl+P` 命令面板的模糊搜索，不靠视觉罗列。

### 5.3 模型与 Provider

- **Base URL**：给格式示例与 Placeholder（缺 `/v1`、协议头错误是最高频的两类错）。
- **API Key**：密码掩码、支持粘贴、加密存储、回显只留首尾 `sk-****...****`。
- **主动验证**：配置完成后不能只允许「保存」，必须能就地测——拉模型列表 / 测试连接 / 鉴权检查 / 网络检查 / Provider 可用性。

### 5.4 任务、Session 与上下文

| 概念 | 定义 | 界面呈现 |
|---|---|---|
| Task | 当前正在处理的具体任务，如「把 C++ 项目迁到鲲鹏」 | 顶部 Tab + Dock 任务列 |
| Session | 任务的完整历史上下文，可 `--resume` 恢复 | `/sessions` 列表 · Session 树 |
| Context | 本次对话已占用的上下文水位 | Inspector 常驻水位条，72% 转 warning，90% 主动建议 `/compact` |

每个任务需具备：Agent Title · 状态 · 当前步骤 · 最近活动 · 运行时间 · Session ID。

### 5.5 Skill 与 Tool 可视化

不输出大量原始日志，而给结构化状态：当前 Skill、Tool 调用列表与各自状态、进度。原始输出**折叠可展开**，默认不占画布。

### 5.6 结果与交付

固定四段：**结论 → 证据 → 下一步 → 产出**。产出区必须给路径与体积，并说明哪些不随报告导出。
支持文件选择、文件夹选择、打包、下载、导出报告。

### 5.7 升级

`devkitai update` 更新客户端，`devkitai skill update` 更新 Skill。过程展示当前版本、目标版本、下载进度、安装状态、更新内容；失败给原因、重试、网络检查与权限提示。

## 6. 关键交互

### 6.1 冷启动追问

用户只说「帮我看看这个项目」时，Agent **不应直接进入无目的执行**，而要做意图识别与追问，并给鲲鹏场景相关的方向：

```text
我可以从以下方向帮你分析：
  [迁移兼容性]  [代码优化]  [性能诊断]  [依赖分析]  [鲲鹏适配检查]
```

### 6.2 执行过程

```text
Thinking → Loading Skill → Calling Tool → Reading Files
        → Editing Files → Running Command → Verifying → Completed
```

界面把这条链路压成固定四行：**状态 + Skill + Tools + 进度**。任何时刻这四行都能回答「在做什么、用什么、到哪一步」，不需要展开日志。

### 6.3 Diff 与改动审查

行级 / 文件级 diff、新增删除修改、文件路径定位。重点不是展示所有代码，而是让用户快速完成一件事：**确认 Agent 是否按预期改动**。

每个 hunk 固定带三行：**为什么 / 证据 / 影响面**。影响面（同类调用点还有几处）最容易被漏掉，却直接决定用户敢不敢按「全部接受」。

竞品分析结论：行业最弱环节就是这一步，**没有一个产品做到 hunk 级接受/拒绝**——这是本产品最大的机会点。

### 6.4 Ask User · 人机协同

```text
? 发现两个可能的迁移方案：
    1. 使用 OpenSSL 兼容方案
    2. 使用鲲鹏原生优化方案
  请选择：> 1
           2
```

原则：**不确定时询问，而不是擅自决策。**

### 6.5 高危操作确认

删除文件 · 批量修改 · 修改核心配置 · 高风险 Shell · 修改系统环境 · 安装卸载软件，一律强制确认。

确认框必须显示**将要执行的原始命令本身**与不可撤销说明，默认焦点在取消。只说「要执行危险操作吗」的确认框等于没确认。

### 6.6 中断：Interrupt → Correct → Resume

```text
传统 CLI                     DevKit AI
Ctrl+C                       Esc
  ↓                            ↓
进程终止                     暂停当前动作 → 保留上下文
上下文全丢                     → 用户纠偏 → 从断点继续
```

**Esc 不只是快捷键，而是人机协同机制。** 中断后输入框必须立即可用并给出提示，否则用户不知道自己已经拿回控制权。

### 6.7 多任务

长任务（大工程迁移、性能采集）必须能后台跑。任务状态徽标复用全局符号体系；`⏸ 等待配置` 是最需要突出的状态——它卡着不动且需要人，要在底栏常驻提示；后台任务完成用**非打断式通知**（底栏变化 + 列表徽标），不抢当前焦点。

### 6.8 长尾对话

任务完成不是 Session 的终点。结果页与输入框保持连续，用户可以接着问「为什么这个方案性能更好」「帮我再优化一下」「生成一份迁移报告」。**不要把任务完成设计成封闭流程。**

### 6.9 快捷键（待终端兼容性验证）

| 快捷键 | 功能 | 快捷键 | 功能 |
|---|---|---|---|
| `Enter` | 发送 / 确认 | `Tab` | 区域切换 |
| `Esc` | 安全中断 / 返回 | `Ctrl+P` | 命令面板 |
| `Ctrl+C` | 复制 / 系统级中断 | `Ctrl+T` | 新建任务 |
| `Ctrl+V` | 粘贴 | `Ctrl+W` | 关闭当前任务 |
| `↑ / ↓` | 历史 / 选项 | `Ctrl+1~9` | 快速切换任务 |

`Ctrl+C` 同时承担「复制」与「系统级中断」两种语义，是本表最大的冲突点，须在实现前裁决（见 §10）。

## 7. 状态体系

### 7.1 四类状态机

| 对象 | 状态 |
|---|---|
| **Agent** | `Idle` · `Running` · `Waiting` · `Suspended` · `Completed` · `Failed` |
| **Tool** | `Pending` · `Running` · `Success` · `Failed` · `Cancelled` |
| **Task** | `Created` · `Running` · `Waiting` · `Suspended` · `Completed` · `Failed` |
| **Connection** | `Disconnected` · `Connecting` · `Connected` · `Failed` |

### 7.2 统一符号与配色

符号先行、颜色其次——16 色终端与 `NO_COLOR` 下形状仍要成立。

| 状态 | 符号 | 色 | 用在哪 |
|---|---|---|---|
| Running / 进行中 | `●` `⠹` | primary | Agent、Tool、Task |
| Waiting / 需要用户 | `?` | warning | Ask User、配置补齐 |
| Suspended / 已暂停 | `⏸` | warning | 后台任务、待配置 |
| Completed / 成功 | `✓` | success | 全部 |
| Failed / 失败 | `✕` | danger | 全部 |
| Pending / 未开始 | `○` | muted | Tool、Plan 步骤 |
| 风险提示 | `⚠` | warning | 结论层，不上色块 |

**颜色三分工不可越界**：Kunpeng 红 `#ED1C24` 只做身份，品牌蓝 `#0077FF` 只做交互，错误红 `#FF4B7B` 只做语义。判据是——看到红色时，该想到「华为鲲鹏」还是「出事了」？两种含义同屏出现即违规。

**数据走色阶，结论走语义色。** bar、火焰图、热力用域色阶；只有被判定为问题的数值与文字才上 warning / danger。50% 的占比、90% 的 CPU 利用率本身都不是错误。

### 7.3 Loading

任何可能超过短暂等待的操作都要有明确反馈：

```text
⠋ Connecting to Provider...
⠋ Loading models...
```

**给不出进度就不画进度条**——不确定进度用不确定态动画，不画假的百分比。要避免的是：用户按了键 → 屏幕无变化 → 以为程序卡死。

### 7.4 错误分类

错误不能直接甩底层错误码，必须经分类与用户化解释，且**三件套齐全：发生了什么 → 为什么 → 怎么解决**。

| 类别 | 文案 | 附带原因 |
|---|---|---|
| 地址 / 格式 | 无法连接到该地址，请检查 Base URL 是否正确 | 缺 `/v1` · 协议头错误 · 拼写错误 |
| 网络 / 代理 | 连接超时，请检查当前网络环境或 VPN / 代理设置 | 代理未生效 · 目标不可达 |
| 鉴权 | API Key 鉴权失败，请确认 Key 是否过期或权限不足 | 过期 · 权限不足 · 账号欠费 |
| 能力缺失 | 未检测到 aarch64 交叉编译工具链 | 附 `[F] 修复` 动作 |

## 8. 页面与组件

### 8.1 信息架构

```text
DevKit AI
├── Home / Welcome
├── Agent Workspace
│   ├── Conversation
│   ├── Agent Status
│   ├── Tool / Skill
│   ├── Diff
│   └── Ask User
├── Task Manager（Running / Waiting / Suspended / Completed）
├── File Explorer
├── Session
├── Skill
├── Model / Provider
└── Settings / Update
```

### 8.2 组件清单

| 组件 | 核心作用 | 归属 |
|---|---|---|
| Welcome | 首次启动、能力介绍 | 页面局部 |
| Prompt | 自然语言输入 | 全局 Shell |
| Command Palette | 命令发现 | 全局 Shell |
| Agent Status | Agent 状态四行 | 通用组件 |

| 屏 | 回答哪个问题 | 关键组件 |

| 任务结果页 | 我得到了什么 | Summary · Hotspot Table · Flame Chart · Source Hotspot · Artifact List |
| 管理配置 | Agent 到底能不能工作 | Settings Nav · Provider Config · Model Selector · Credential Field · Connection Test · Error |

管理配置把**服务器 / 账号 / 模型**收在同一页（分类 → 列表 → 详情），三类共用一条主线：**每一项都必须能就地验证**。服务器页把"连上之后这台机器能不能干活"逐条探测（架构 / 系统 / DevKit / 编译器 / `perf` 权限 / 交叉工具链），每个不合格项直接带修复动作；账号页是错误体系与凭据纪律的样板屏，失败信息除三件套外还要给**影响面**——令牌过期不阻断 Agent，但会让改动失去案例库证据。

结果页的信息结构对齐 DevKit Web 端「热点函数分析」：Top 30 热点调用栈表（函数/调用栈 · 周期数占比 · 周期数 · 进程名 · 共享库/文件）、火焰图（用户态 / 内核态 / 其他）、源码级逐行百分比。**字段名与分组方式沿用 Web 端，用户在两端之间不需要做术语翻译**；只有两处按 TUI 规则改写：红色退出数据层（语义红只表示「出事了」），紫色搜索标记改为背景反显（16 色下色相不可靠）。

## 9. 设计原则

1. **状态优先**——用户首先要知道「现在发生了什么」，而不是先看到大量文本。
2. **过程透明**——Agent 可以自主执行，但执行过程必须可观察。
3. **用户可控**——任何时候都能 Pause / Interrupt / Correct / Confirm / Resume。
4. **渐进式信息披露**——默认给状态 + 核心结果，需要时再展开 Tool → 参数 → 原始输出 → 日志。
5. **错误可理解**——从 `HTTP 500` / `Connection Refused` 转成「发生了什么 → 为什么 → 怎么解决」。
6. **Agent First 而非 Chat First**——核心对象是 Task / Agent / Skill / Tool / File / Result，不是 User / Message / Message。
7. **画不下就显式说**——`… 24 more`、`3 帧过窄未显示`、`9 行未展开`。悄悄省略会把「我看全了」变成错觉，比不画更危险。

### 9.1 本次设计重点解决的六个问题

不以功能数量衡量，只看这六问是否被答上：

| # | 问题 | 靠什么解 |
|---|---|---|
| ① | 我能不能马上开始？ | 启动 · 环境检测 · 远程连接 |
| ② | Agent 到底能不能工作？ | Model / Provider / API Key / Connection（管理配置页） |
| ③ | Agent 到底在干什么？ | Agent 状态 · Skill · Tool · Streaming · Progress |
| ④ | Agent 有没有跑偏？ | Diff · Ask User · Checkpoint · Interrupt |
| ⑤ | 我有很多任务怎么办？ | Task / Session / Background / Switch |
| ⑥ | 做完之后我得到了什么？ | Summary · Files · Diff · Export · Next Step |

### 9.2 体验闭环

```text
快速接入 → 明确任务 → Agent 执行 →  可观察 Observe
                                  ↘ 可控制 Control  ↘ 结果交付 → Session 延续
```

> **让 Agent 自主执行，让用户始终看得见、管得住、拿得到结果。**

### 11.3 七条关键任务链路（S3 原型范围）

1. 首次启动 → 环境检测 → 能力安装
2. 模型配置 → 失败诊断 → 连接成功

### 11.5 评审判据

每一阶段评审只问一句：

> **是否能让用户在纯终端环境下，建立接近 IDE 的「任务感、状态感和控制感」，而不是仅仅得到一个更漂亮的 CLI。**

配套的三条硬判据：①遮住所有蓝色，还能说清「我现在选中的是什么」吗？能，说明蓝铺多了。②遮住颜色，状态还读得出来吗？③每条结论旁边有没有可点开的证据？
