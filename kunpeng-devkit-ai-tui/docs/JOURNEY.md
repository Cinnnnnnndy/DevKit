## 1. 旅程地图

```
阶段1 初始化配置 ─▸ 阶段2 代码迁移 ─▸ 阶段3 验证编译 ─┬─▸ 阶段4 代码优化 ─▸ 阶段5 参数优化 ─▸ 阶段6 场景化调优
  开屏引导          自然语言触发      一键编译       │    高亮 + diff      方案对比图表       业务场景深调
  能力安装          Plan 生成→确认    结果反馈       │    Plan 生成        性能前后对比
  Skill 配置        配置补齐          ✕ 失败 ───────┘    配置补齐            配置补齐
  多任务管理        改写结果展示      ✓ 通过              下一步引导          下一步引导
                    下一步引导
                     ▲                 ▲                  ▲                  ▲
                     └───────── 三个贯穿全流程的连接组织 ────────────┘
                        P27 配置补齐 · P28 下一步引导 · P29 多任务管理
```

这条旅程补出了场景章节没覆盖的三个环节：**首次配置 · 配置补齐 · 下一步引导**——它们不属于任何单一场景，而是把六个阶段串成连续旅程的连接组织。

| 阶段 | 用户目标 | 关键触点 | TUI 屏 / Pattern |
|---|---|---|---|
| 1 初始化配置 | 熟悉系统，搭好基础环境 | 开屏与初始对话引导 · 能力安装 · Skill 配置 · 多 terminal 并发任务管理 | Landing Screen · Capability Manager · **P29 多任务** · P14 索引状态 |
| 2 代码迁移 | 把现有代码迁到鲲鹏 | 自然语言触发 · Plan 生成与确认 · **配置补齐**（工具链/输出目录/并行度）· 改写结果 · 下一步引导 | P02 Plan · **P27 配置补齐** · P05 Diff · P11 Tool · **P28 下一步** |
| 3 验证编译 | 确认迁移后能编译能跑 | 一键验证 · 编译执行 · 成功/失败即时反馈 | P01 Timeline · P12 Summary · 失败分支转 Diagnose（P03/P04） |
| 4 代码优化 | 进一步提升质量与性能 | 自然语言或系统引导触发 · Plan 生成 · 配置补齐 · **高亮 + diff 对比** · 下一步引导 | P02 · P27 · **P05 Diff Review** · P28 |
| 5 参数优化 | 调参数达到最佳性能 | 触发 · Plan 生成 · 配置补齐 · **优化方案图表 + 性能前后对比图表** · 下一步引导 | P02 · P27 · **方案对比表 + Before/After（T1/T2）** · P28 |
| 6 场景化调优 | 针对具体业务场景深度调优 | 从参数优化结果页引导进入 | Workspace 切换（P23）· 场景 profile 选择 · P21 Live Canvas |

### 旅程的四个特征 → 四条设计要求

1. **自然语言驱动**——迁移/代码优化/参数优化三个核心环节都由自然语言触发，所以输入栏必须常驻且是第一入口，命令只是等价快捷方式。
2. **配置补齐反复出现**——三个阶段都有，说明它不是某个场景的细节而是**系统级 Pattern（P27）**，必须统一设计。
3. **结果可视化按阶段分化**——代码阶段看 diff 和高亮，参数阶段看图表。同一个"结果页"在不同阶段要换渲染层：代码 T0，参数 T1/T2。
4. **线性为主、关键节点分支**——编译失败要能就地转诊断，参数调优后要能进场景化。所以**下一步引导（P28）必须是状态相关的**，不能给固定菜单。

## 2. Demo 故事线

主角：性能工程师，要把一套 x86 上的 nginx 迁到鲲鹏 ARM64 并调到可上线性能。

**演示环境：纯本地，零前置。** Runtime 随二进制本地起，不需要填服务器地址、不需要凭据、不需要网络。`devkitai` 一敲就进工作台——这是演示的第一个说服点，也是"原生 TUI 单二进制交付"的直接兑现。

| 幕 | 发生什么 | 观众看到的"哇点" |
|---|---|---|
| ① 开场 | 本地终端敲 `devkitai`，全屏工作台直接起来，**零配置、零登录**。首屏显示环境已就绪 + 检测到 3 项能力未装，一键装好。 | **一条命令进工作台**——不用装 IDE、不用配环境、不用连远端 |
| ② 提需求 | 直接说"把 ./nginx 迁到鲲鹏"。系统不立刻动手，先出 5 步 Plan 并标注要调哪些工具。 | AI 先给计划再执行，计划可改 |
| ③ 补配置 | 执行到"编译验证"时停下：本地没探测到 aarch64 交叉编译工具链，需要指定路径和输出目录。就地弹层收集（带 Tab 路径补全），填完**接着原来那一步继续**。 | 不是一开始灌一堆表单，**要用到才问，且说明为什么要** |
| ④ 出报告 | 兼容性 82%，2 个 Critical、8 个 Warning、21 个可自动修。文件风险热力一眼定位到 crypto.c。 | 热力图定位问题文件 |
| ⑤ 审改动 | 逐个看 patch：`_mm_pause()` → `asm("yield")`，附知识库案例编号和 ARM 手册章节。 | **每条改动都有证据可溯源** |
| ⑥ 编译翻车 | Build 失败。系统不只报错，直接转入诊断：根因链路图指到内存对齐，置信度 91%，给修复方案。修完重编，PASS。 | **失败是分支不是死路**——就地转诊断 |
| ⑦ 看性能 | 下一步引导给三条建议，选"跑性能基线"。Trace 出来：HBM 持续饱和而 NPU 有气泡 → memory-bound。 | 并置才看得出的结论，AI 直接标在图上 |
| ⑧ 调参数 | 参数优化给三套方案对比表（QPS/P99/CPU/内存），推荐方案 A：worker 数对齐 64 物理核 + NUMA 亲和绑定。应用后 QPS 42k → 61k。 | **方案对比而非单一建议**，改动都带"为什么" |
| ⑨ 场景化 | 引导进入场景化调优：选"高并发短连接" profile，再针对性调一轮。 | 调优不是一次性的，按业务场景分档 |
| ⑩ 收尾 | Session Summary：21 修复 / 2 待人工 / Build PASS / QPS +45%。导出报告。 | 全程可追溯，一份报告交差 |

**串讲节奏建议**：①–② 讲"为什么是 TUI"（2 分钟）· ③–⑥ 讲"AI 怎么把活干完且可审计"（5 分钟，**⑥ 编译翻车是全场最关键的一幕**，它证明系统能处理不顺利的情况）· ⑦–⑨ 讲"可观测与调优深度"（5 分钟）· ⑩ 收。总时长 12–15 分钟。

## 2.5 演示画布：1920 × 1080 固定标准

**1920 × 1080 指的是终端窗口本身**——那台被演示的"屏幕"是 1080p，而不是整个演示页面是 1080p。所以 `.term` 的尺寸写死为 `1920px × 1080px`，串讲用的头部、幕轨、右侧说明卡是**围在它外面**的额外版面，整台舞台因此是 2422 × 1282。舞台再用 `transform: scale()` 等比缩进当前视口并居中——**任何屏幕上看到的都是同一张设计稿**，只是被整体缩放。这样评审、投屏、截图、录屏拿到的构图完全一致。

（早先误解成"整页 1080p"，终端只占其中一部分，等于把这台终端按 1080p 的一半来设计了。区别很实在：现在终端的字符网格是 **199 × 43**，之前只有 156 × 37。）

版面按三段切：顶部 74px 的头部（标识 / 产品名 / 播放控制），底部 74px 的十幕轨道，中间是主体——左边终端占满剩余宽度，右边 424px 竖排三张卡片：**本幕说明与哇点** → **本幕在旅程中的位置** → **串讲节奏**。中间那张把十幕映射回六阶段旅程（`ACT2STAGE = [1,2,1,2,2,3,4,5,6,6]`），当前阶段高亮、已过阶段变灰、每行右侧标出属于它的幕号，讲的人随时知道自己走到旅程哪一段。

终端不是被放大的小终端，而是**真的变大了**——字符单元格提到 16px，字符网格 **199×43**。这个尺寸标签现在是运行时量出来的（测一次 `M` 的实际 advance 与行高，再除屏幕盒子），不是写死的数字，改任何字号它都跟着变。这也顺带验证了一件事：我们的信息架构在 199 列宽下不会散架——双栏画布各自还有 90+ 列，够放 diff 和证据。

## 3. 新增 Patterns

### P27 · Config Completion 配置补齐

**反模式**：任务开始前甩一张大表单要求填完所有可能用到的配置。用户此时既不知道哪些是必需的，也不知道为什么要。

**本 Pattern**：让 Agent 先跑，**执行到真正需要某项配置的那一步才暂停询问**，问的时候必须说明"为什么这一步需要它"，填完**从暂停处继续**而不是重启任务。

| 规则 | 说明 |
|---|---|
| 就地暂停 | Timeline 该步标 `⏸`，不回滚已完成步骤；补齐后原地续跑 |
| 解释必需性 | 浮层顶部一句话说明为什么需要——这是信任的关键 |
| 敏感信息隔离 | 密码/密钥 masked 输入，标注「仅本次会话 · 不入上下文 · 不写日志」并真的做到 |
| 提供退路 | 必须有「跳过此步」选项，不能把用户堵死 |
| 记忆与复用 | 非敏感项（工具链路径、输出目录）存入会话，同工程下次不再问 |
| 批量合并 | 同一步需要多项时一次问完，不要连续弹三次 |

```
│ Agent
│ ● Analyze dependency               18 libs
│ ● Generate patches                 12 files
│ ⏸ Build verify —— 需要补充 3 项配置才能继续
│
│   ╭─ 补充配置 ────────────────────────────────────────╮
│   │ 为什么需要：未探测到 aarch64 交叉编译工具链        │
│   │                                                   │
│   │ 工具链路径   ❯ /usr/bin/aarch64-linux-gnu-▌        │
│   │ 输出目录     ❯ ./build-arm64             [Tab] 补全 │
│   │ 并行度       ❯ 16                检测到 16 逻辑核   │
│   │ 敏感项（如 SQL 迁移的库口令）走 masked 输入，见规则 │
│   │                                                   │
│   │ [↵] 填完继续   [S] 跳过验证   [Esc] 中止任务        │
│   ╰───────────────────────────────────────────────────╯
│ ○ Performance check
```

### P28 · Next-Step Guidance 下一步引导

线性旅程能不能真的走下去，取决于每一段结束时系统有没有把下一步铺好。**禁止在阶段结束后甩回空白输入框**——那是把"接下来该干嘛"的成本转嫁给用户。

| 规则 | 说明 |
|---|---|
| **状态相关** | Build PASS → 首选"跑性能基线"；Build FAIL → 首选"看诊断报告" |
| 1–3 条 | 超过 3 条就成了菜单，失去引导意义 |
| 带耗时预估 | 让用户判断现在做还是待会做 |
| 首条可回车直走 | 默认高亮，Enter 即执行 |
| 保留自由输入 | 建议之下永远留一行 `❯`——引导是加速器不是围栏 |

与 P12 Session Summary 的分工：P12 讲**刚才发生了什么**（结果与产物），P28 讲**接下来能做什么**。两者同屏、上下相邻。

```
│ ✓ Build PASS   21 fixed · 2 manual · 3m12s
│
│ 下一步
│  ▸ [1] 跑性能基线，看迁移后掉了多少        ~2min
│    [2] 处理剩下 2 处需人工确认的改动
│    [3] 换个工程继续迁移
│ ❯ 或直接说你想干什么▌
```

### P29 · Multi-Task Manager 多任务并发

迁移大工程、性能采集、压测都是分钟级任务，必须能后台跑并行推进——这是常驻进程相对 CLI 的核心增量之一。

| 规则 | 说明 |
|---|---|
| 状态徽标统一 | 复用全局符号体系 `✓ ▶ ○ ⚠ ✕`，并显示已用/预估时长 |
| **⏸ 等待配置最高优先级** | 此状态卡着不动且需要人介入，必须在底栏常驻提示，否则任务会被遗忘 |
| 非打断式通知 | 后台任务完成时底栏提示 + 列表徽标变化，**不抢当前焦点**、不弹浮层 |
| 快速切换 | `Alt+1..9` 直达；每个任务保留自己的 Workspace 布局与滚动位置 |
| 资源提示 | 并发采集任务会互相干扰性能数据——同时运行 profiler 类任务时给出警告 |

```
┌tasks─────────────────────── [Alt+1..9]切换 [n]新建 [k]终止 ─┐
│ ● 1 migrate nginx          ✓ 完成    Build PASS  12:04     │
│ ▶ 2 optimize qwen-72b      ⠹ 采集中  02:14 / ~05:00        │
│ ○ 3 diagnose crash.log     排队中                          │
│ ⚠ 4 migrate order-svc      ⏸ 等待补充配置   [↵] 去处理      │
└────────────────────────────────────────────────────────────┘
```

### 阶段 5 · 参数优化结果

```
┌param tuning─nginx @ Kunpeng920──────────────────────────┐
│ 方案对比           QPS         P99      CPU      内存    │
│ baseline      ████░░░░░ 42k   18ms   ███░░ 62%   4.2G   │
│ 方案 A ★推荐   ██████░░░ 61k   12ms   ████░ 78%   5.1G   │
│ 方案 B 激进    █████░░░░ 55k    9ms   █████ 88%   6.8G   │
├──────────────────────────────────────────────────────────┤
│ 方案 A 的改动与理由                                      │
│  worker_processes    auto → 64     ← 对齐 64 物理核       │
│  worker_connections  1024 → 8192   ← 匹配实测并发水位     │
│  numa 绑定            off → per-worker ← 消除跨 NUMA 访问 │
│                                                          │
│ [Y] 应用方案 A  [D] 看完整 diff  [B] 再压测  [C] 自定义   │
└──────────────────────────────────────────────────────────┘
```

三条纪律：① 给方案**对比**而非单一建议（工程师要自己判断取舍）；② 每条改动带**为什么**，且尽量引用同屏可验证的证据（"见热力"可 Enter 跳回 NUMA 图）；③ 副作用要显式（方案 B 的 P99 更好但内存涨到 6.8G，用 warning 色标出）。
