# Kunpeng DevKit AI — Visual System（PTO → TUI 翻译）

> Version 0.5 · 继承 PTO Design System 4.1（529 tokens · Dark-first · Inter + JetBrains Mono）

---

## 0. 继承什么，翻译什么

Kunpeng DevKit AI 直接继承 PTO Design System 的 token 体系与设计原则。但 Web 与终端表达能力差异巨大，**本文档的核心工作是把 PTO 的 web token 翻译成终端可实现的 TUI token**，而不是简单复制色值。

| PTO（Web） | 终端能力 | 翻译策略 |
|---|---|---|
| 6 级表面 ramp | ✓ 真彩逐格背景色 | **1:1 直译**，truecolor 下完全可复现 |
| 4 级前景透明度 | ✗ 无 alpha 通道 | **预合成**——按已知表面色离线拍平为实色 |
| 3 级阴影 | ✗ 无阴影 | **改用边框强度 + 表面步进**表达层级 |
| 5 级圆角 | △ 仅两档制表符 | sm/md → `┌┐└┘`；lg/xl/pill → `╭╮╰╯` |
| 4px 基准间距 | △ 单元格非正方 | **拆成 space-x（列）与 space-y（行）双轴** |
| 6 级字号 + 2 字族 | ✗ 单一字号，全等宽 | **层级改由 粗细 + 色阶 + 大写字距 + 缩进 编码** |
| 5 条数据可视化色阶 | ✓ 真彩 | **1:1 直译**，正是热力图/Trace 密度带所需 |
| 动效 duration + easing | △ 帧驱动 | 换算为帧数（30fps）；保留"动效只服务于功能" |

**原样保留的第一性原则**：中性表面承载布局，强调色传递语义 · 不在 UI 面板背景使用大面积饱和填充 · 高亮色阶仅用于数据可视化 · 每个表面只选一种强调机制 · 动效只服务于功能，无装饰性循环动画。

## 0.4 能力天花板修正 —— 两条推翻旧假设的发现 ⭐

调研 Lip Gloss 的样式 API 与 TUIStudio 的属性面板后，本文档前几节里两条"终端做不到"的判断需要修正：

| 旧判断 | 修正 | 影响 |
|---|---|---|
| 终端无渐变，色阶要手写 hex | **`Blend1D()` / `Blend2D()` 可程序化生成渐变**，另有 `Darken/Lighten/Complementary/Alpha` 色彩运算 | 域色映射的 800→300 各档**可由端点算出**，保证感知均匀，不必手写十几个 hex |
| AI 标注"叠在数据之上"只是概念表述 | **`Compositor` + `Layer` 支持真正的分层合成** | **P26 AI 标注层从设计概念变成架构决策**——标注是独立图层，可整层开关、整层调透明度 |

其它此前未覆盖的能力：五种下划线（single/double/**curly**/dotted/dashed，curly 可用于标错，沿用 IDE 语义）· 超链接（`Hyperlink()`）· 自定义内外边距填充字符（`PaddingChar('·')`）· Tree 枚举器（Default/Rounded，直接对应工程树缩进引导线）· List 五种枚举器（Arabic/Alphabet/Roman/Bullet/Tree）。TUIStudio 的属性面板里甚至有 Drop Shadow 与 Opacity 滑块。

> **纪律不变，天花板要重认。** 前面写的"终端无阴影、无 alpha、圆角只有两档"是**基于最保守终端的假设**——为了降级它们仍然成立，但在支持真彩的现代终端 + Textual/Lip Gloss 这类框架下，可用手段比想象中多。完整的视觉能力分析见 `../web/visual-analysis.html`。

## 0.5 Chrome 层 vs Canvas 层 —— 不是所有东西都用字符拼 ⭐

TUI 常被误解成"全部由 ASCII 拼出来的界面"。**不是。** 现代 TUI 框架提供的是**真正的 UI 组件系统**——有表面层、边框、圆角、状态、图标、徽标、滚动条。字符拼接只是其中一种渲染手段，只该用在特定地方。

| 层 | 包含 | 渲染方式 | 必须具备 |
|---|---|---|---|
| **Chrome 层**（框架/结构） | Header · Dock（任务/工程树/工具）· Tab Bar · 状态栏 · 浮层 · 列表（Plan/Evidence/下一步）· 表单 · 命令面板 | **真 UI 组件**<br>Textual Widget + TCSS | 表面层级 · 边框强度 · 圆角 · **hover/selected/focus/disabled 四态** · 图标 · 徽标计数 · 缩进引导线 · 滚动条指示 |
| **Canvas 层**（数据/读数） | Braille 曲线 · 热力网格 · Trace 密度带 · Gauge/Sparkline · 散点 · diff · 日志 · 代码 | **字符网格**<br>Rich renderable | 渲染分层 T1–T3 · 域色映射 · 顺序/分类色阶纪律 · 等宽对齐 |

### 判断标准

> 问一句：这块内容是「结构」还是「读数」？

- **结构**——用户在这里做的是选择、导航、切换、确认 → Chrome 层，用组件，需要状态表达
- **读数**——用户在这里做的是看数值、比大小、找异常 → Canvas 层，用字符，需要密度与对齐

两者混在一个面板里时，按**子区域**分别处理：Migration Report = Issue 列表（组件）+ 兼容性 bar / 风险热力（字符）；算子表 = 行选中与排序（组件）+ 单元格里的 bar（字符）。

### Chrome 组件与 PTO token 对应

| 组件 | 结构 | PTO token |
|---|---|---|
| 分区标题 | 折叠箭头 + 大写字距标签 + 右侧计数徽标 | label 11px · fg-muted · surface-2 pill |
| 列表项 | 图标 + 主标签（省略号截断）+ 徽标 + 右侧元信息 | radius-sm · hover=surface-3 · selected=state-selected + 左侧 2px accent |
| 树节点 | **缩进引导线** + 展开箭头 + 文件名 + 风险条 | gutter=fg-disabled · 风险条用域色阶 |
| Tab | 状态点 + 标题 + 关闭 + 新建；选中态顶部 2px 品牌色 | radius-lg 上圆角 · 选中底色=background |
| 状态栏 | **分段式**，段间 1px 分隔；当前 Workspace 段用品牌底色 | surface-2 · border-subtle · state-selected |
| 结构化列表 | 序号 + 主副两行 + 右侧耗时/动作 + 工具 tag | radius-md · hover · on=state-selected + border |
| Header chip | 状态点 + 文本，pill 形态 | radius-pill · surface-3 · border-subtle |

### 为什么这条重要

1. **状态表达**——字符拼不出 hover/selected 的层次感，而"我现在选中的是哪一项"是工作台的基本诉求
2. **自适应**——组件能随宽度伸缩截断，字符对齐依赖固定列宽，一变窄就崩
3. **可维护**——TCSS 改一处全局生效；字符拼接每处都要重算列宽（本规范里那些 ASCII 框是靠脚本算宽度才对齐的，这恰恰说明它不适合做框架）

反过来，**数据区也不能用组件**：64 核热力网格如果用 64 个 widget，密度、对齐、性能全都做不到。**两层各司其职，边界清晰。**

## 1. Colors

### 1.1 Surfaces — 1:1 直译

```
--background          #101010   应用底
--background-elevated #141414   面板底
--surface-1           #161616   卡片
--surface-2           #1C1C1C   表头 / 工具栏
--surface-3           #262626   hover
--surface-4           #313131   选中 / 节点高亮
```

### 1.2 Foreground — 预合成为实色

终端无 alpha 通道，PTO 的 `rgba(255,255,255,.90/.60/.40/.25)` 必须按所叠表面离线拍平。**下表可直接写进配色文件。**

| level | on #101010 | on #161616 | on #1C1C1C | on #262626 | on #313131 |
|---|---|---|---|---|---|
| foreground .90 | #E7E7E7 | #E8E8E8 | #E8E8E8 | #E9E9E9 | #EAEAEA |
| secondary .60 | #9F9F9F | #A2A2A2 | #A4A4A4 | #A8A8A8 | #ADADAD |
| muted .40 | #707070 | #737373 | #777777 | #7D7D7D | #838383 |
| disabled .25 | #4C4C4C | #505050 | #555555 | #5C5C5C | #646464 |

> **降级注意**：disabled .25 拍平后对比度约 2.2:1，在终端上比 Web 更难读（无字体抗锯齿加持）。规范：TUI 中 disabled 文本最低使用 muted 档（#707070），disabled 档只用于分隔线与装饰性字符。

### 1.3 Primary & Semantic

DevKit 品牌色 `#0077FF` 取代 PTO 原本的 `#4369EF`。

```
--primary        #0077FF   填充 / 边框 / 焦点底色（不用于文本）
--primary-hover  #3D98FF   一切文本 / 链接 / 图标
--accent         #7C8DB8   元数据 / ID / 次级强调
--success        #04D793   ✓ 完成 / 通过
--warning        #FFAA3B   ⚠ 风险 / 待重启 / 非致命异常
--danger         #FF4B7B   ✕ 失败 / Critical / 高危操作
```

**品牌色替换带来的两条硬约束**（实测）：

**① 对比度不足，文本不能直接用品牌色。**

| 用色 | on #101010 | on #161616 | on #1C1C1C | 结论 |
|---|---|---|---|---|
| `#0077FF` primary | 4.61 | 4.38 | **4.12** | 深色表面上不达 AA |
| `#3D98FF` primary-hover | 6.46 | 6.15 | 5.79 | 全部达标 |

规范：**品牌色只用于填充、边框、焦点底色；一切文本 / 链接 / 图标用 `--primary-hover #3D98FF`**。这与 PTO 原色的情况不同——旧的 #4369EF 更暗，靠 hover 档提亮；新品牌色更亮更饱和，问题变成"纯色在深灰表面上灰度差不够"。

**② 与 data-viz 的 copy-blue 撞色。** 品牌色色相 212°，PTO 的 `copy-blue` 色阶色相 219°，**只差 7°**。在终端里（无法靠尺寸/位置区分）用户无法分辨"这条泳道是 CPU"还是"这条泳道被选中了"。解决方案见 1.5 域色映射。

### 1.4 State Overlays — 预合成（叠在 surface-2）

```
base       #1C1C1C
hover +6%  #2A2A2A
press +10% #333333
selected   #18293C
focus      #162E49
```

终端无 focus ring（无法画外发光轮廓）。**替代方案：焦点 = 背景色 `#162E49` + 左侧 `▎` 标记 + 边框升为 border-strong 三者组合**，三选二即可辨识，兼顾 16 色降级。

### 1.5 Highlight Ramps — 顺序 vs 分类，不要混用 ⭐

这五条色阶的命名（copy · l0a · accum · ub · mte）本身就是**昇腾 NPU 的功能单元名**——它们是**分类色（categorical）**，用来区分"这是哪个单元"，**不是**用来表达"值有多大"。

| 用途 | 取色方式 | DevKit 场景 |
|---|---|---|
| **顺序 / 强度** | **同一条色阶内取 5 档** `800 → 600 → 500 → 400 → 300`（暗→亮） | NUMA 核心利用率、文件风险热力、Trace 密度、内存占用 |
| **分类 / 身份** | **每类取一条色阶**，各用其 `-400` 档 | Trace 泳道身份（CPU / NPU / HBM / MTE / UB）、算子类别 |
| **分类 + 强度** | 色阶定身份，**档位定强度** | Trace 密度带——*哪条泳道* 用色阶，*多忙* 用档位 |

```
✗ 错误：用五条不同色阶表达"利用率高低"
        五种色相混在一起，读者无法建立"哪个更热"的直觉

✓ 正确：同一条色阶取 5 档，暗→亮 = 低→高
   accum-orange  #773303 → #A44604 → #D15905 → #FA8838 → #FBAB74

✓ 正确：分类用色阶，强度用档位
   CPU  ub-green     #4D7209 → #86C70F → #B3F141 → #CAF57A
   NPU  l0a-violet   #3F0675 → #6E0ACD → #9B3CF6 → #B977F9
   HBM  accum-orange #773303 → #D15905 → #FA8838 → #FBAB74
```

### 1.6 域色映射 — 蓝色专属品牌，数据色从非蓝取 ⭐

品牌蓝会出现在色块上（进度条、选中底色、焦点），因此 **`copy-blue` 必须退出 TUI 的数据可视化色板**。全产品建立固定域色映射，同一个观测对象在任何页面都是同一个色相：

| 域 | 色阶 | 色相距品牌 | 档位 800→300 |
|---|---|---|---|
| UI / 品牌 / 焦点 | brand blue | 212° — | `#0077FF` 填充 · `#3D98FF` 文本 |
| CPU | ub-green | 131° | `#4D7209 → #86C70F → #B3F141 → #CAF57A` |
| NPU / GPU | l0a-violet | 59° | `#3F0675 → #6E0ACD → #9B3CF6 → #B977F9` |
| Memory / HBM | accum-orange | 173° | `#773303 → #D15905 → #FA8838 → #FBAB74` |
| Network / IO | mte-amber | 167° | `#713F12 → #CA8A04 → #F4CB22 → #FBDC59` |
| ~~copy-blue~~ | **已退出** | **7° ✕** | 与品牌撞色，TUI 中停用 |

**还有一条形状层的分离规则，比调色相更可靠。** 语义色与数据色阶在色相上仍有邻近（warning 35° vs accum-orange 25°）。终端里最终靠**字形**而非色相区分：

- **语义色只上字符与短文本**（`✓ ⚠ ✕`、状态标签），**永不上色块**
- **数据色阶只上色块与点阵**（`█▓▒░ ⣿`），**永不上文字**

这与 PTO 自身的"Badge 语义色只作用于文字，底面保持中性"是同一条纪律的两面。有了它，即使色相接近也不会误读。

> **语义色不参与数据可视化。** `success / warning / danger` 只表达**状态判断**（通过 / 风险 / 失败），不表达**数值大小**。一个 90% 的 CPU 利用率本身不是"错误"——它应该用顺序色阶的最亮档，而不是 danger 红。只有当 AI 判定它构成问题时，才由 P26 标注层叠加 danger 色的描边与角标。**把"数据"和"结论"用不同的颜色系统表达，是这套规范里最重要的一条用色纪律。**

## 2. Typography — 六级字号如何塌缩到一级

PTO 有 6 级字号 × 3 种字重 × 2 个字族；终端**只有一个字号、一个字族**。层级必须由其它维度重新编码。

| PTO 级别 | Web 规格 | TUI 编码方案 |
|---|---|---|
| display | 28px / 700 | BOLD + primary 色 + 下方整行分隔线 |
| title-1 | 20px / 600 | BOLD + foreground .90 + 上方留 1 空行 |
| title-2 | 16px / 600 | BOLD + 嵌入面板上边框 `┌kernels────┐` |
| body | 14px / 400 | 常规 + foreground .90 |
| body-sm | 12px / 400 | 常规 + secondary .60 |
| label | 11px / 500 / +0.5px | **muted .40 + 全大写 + 字间插空格** |

**关键技法**：PTO label 的 `letter-spacing:+0.5px` 在终端无法用亚字符实现，但可以**在字符间插入空格**模拟——`PASS STAGE` → `P A S S  S T A G E`。仅用于分区标签这类短文本，长文本禁用。

**title-2 一处不按表执行，原因写清楚：不加 BOLD。** 落地到 Canvas 层的组件
（`docs/COMPONENT.md`「Canvas 层的框」）之后，一屏经常同时有 3–6 个 title-2
（BrailleChart × 1–2、CoreHeatmap、KernelTable、Console、Evidence），实测
把这几个标题全部加粗，读起来和 TabBar 当前标签页那一处**真正需要独占的
BOLD**互相打架——一眼扫过去分不出谁是"当前对象"、谁只是"这块内容的名字"。
这正是本文档 §"强调色配额"那条原则（"当一屏有十几处蓝，工程师就无法靠余光
找到我现在在哪"）用在字重上的同一个坑：BOLD 一旦不再稀缺就不再是强调。
边框本身已经把标题和正文分开了，不需要再加字重去做同一件事——所以这里的
判据改成"**嵌入边框 + secondary 色**，BOLD 留给 TabBar 当前标签页那类
真正唯一的当前对象"。display / title-1 两档没有这个"同屏多个"的问题，
按表执行。

### 字族语义的替代编码

PTO 用 **Inter（UI）+ JetBrains Mono（数据）** 区分"叙述"与"数据"。终端全等宽，这个区分会丢失。替代：

| PTO 用法 | TUI 替代编码 |
|---|---|
| mono 表示 ID / 算子名 | accent 色 `#7C8DB8` |
| mono 表示数值 / 指标 | **右对齐 + 固定小数位** + secondary 色 |
| mono 表示代码 | 缩进 2 格 + 语法高亮 |
| sans 表示叙述文本 | 默认态，不加任何修饰 |

**推荐终端字体**（需含 Braille U+2800–28FF 与 CJK）：JetBrains Mono NL · Fira Code · Sarasa Term SC（更纱黑体，CJK 等宽对齐最佳）。启动时探测 braille 字形宽度，缺失则 T2 降级到 T1。

## 3. Spacing & Grid — 单轴间距必须拆成双轴

终端单元格不是正方形——典型比例约 1:2（宽 ≈ 8px，高 ≈ 17–20px）。用一套阶梯同时管水平和垂直，必然在某一方向失真。

| PTO token | Web | space-x（列） | space-y（行） | 用途 |
|---|---|---|---|---|
| --space-1 | 4px | 0 col | 0 row | 终端无法表达，向上取到 space-2 |
| --space-2 | 8px | 1 col | 0 row | 行内元素间隙 |
| --space-3 | 12px | 2 col | 0 row | 表格列间距 |
| --space-4 | 16px | 2 col | 1 row | 面板内边距、区块间距 |
| --space-5 | 20px | 3 col | 1 row | 面板之间 |
| --space-6 | 24px | 3 col | 2 row | 大区块分隔 |

**纪律不变**：PTO 规定"不使用任意像素值（7px、13px）"。TUI 版对应——**不使用任意单元格数**。所有留白只能取上表六档，代码里禁止裸数字 padding。

## 4. Elevation & Border — 没有阴影怎么做层级

| PTO 阴影 | Web 用途 | TUI 替代 |
|---|---|---|
| --shadow-sm | chips · pills | surface-2 底 + border-subtle |
| --shadow-md | floating panels | surface-1 底 + border-default + 圆角 `╭╮╰╯` |
| --shadow-lg | modals · overlays | surface-1 底 + **border-strong** + 圆角 + **底层整体降到 disabled 色阶** |

最后一条是终端里表达"模态浮起"的关键——既然不能给浮层加阴影，就**把底层压暗**（所有前景色降一档），浮层保持正常色阶。等价于 Web 的遮罩层，且 16 色下依然成立。

### Border 预合成

| level | on #101010 | on #161616 | on #1C1C1C | on #262626 |
|---|---|---|---|---|
| border-subtle .06 | #1E1E1E | #242424 | #2A2A2A | #333333 |
| border-default .10 | #282828 | #2D2D2D | #333333 | #3C3C3C |
| border-strong .16 | #363636 | #3B3B3B | #404040 | #494949 |

### Radius — 5 档塌缩为 2 档

```
--radius-sm  6px  ┐
--radius-md  8px  ┴─▸ 直角  ┌────┐   表格、内嵌块、工具栏
                           └────┘
--radius-lg  12px ┐
--radius-xl  16px ├─▸ 圆角  ╭────╮   主面板、浮层、卡片
--radius-pill     ┘        ╰────╯

pill 在终端无对应形态 → 用「反色 + 前后各留 1 空格」表达 chip：
   ␣124 ops␣    ␣1.24ms␣    ␣fp16␣    （背景 #2A2A2A）
```

## 5. Motion

PTO 原则原样继承：**动效只服务于功能。无装饰性循环动画，无内容区持续播放。** 这条在 TUI 里比 Web 更重要——终端重绘成本高，远程 SSH 下每一帧都是带宽。

| PTO token | Web | TUI @30fps | 用途 |
|---|---|---|---|
| --duration-fast | 100ms | 3 帧 | hover / 选中态 / 焦点移动 |
| --duration-base | 200ms | 6 帧 | 面板切换 / 分栏展开 |
| --duration-slow | 350ms | 10 帧 | 模态浮层进出 / Workspace 切换 |

**允许**：Braille spinner（仅真实 pending 的工具调用）· 进度填充（有确定进度时）· `▶` 呼吸（Timeline 当前步，1s 周期）· 逐行 reveal（流式输出）。

**禁止**：常驻装饰性动画（跑马灯、闪烁边框、彩虹渐变）· 无进度信息时的假进度条 · 全屏重绘式转场。

**远程降级**：检测到高延迟（RTT > 80ms）时自动关闭所有过渡动画，只保留 spinner 与进度条，spinner 降到 4fps。

## 6. 落地：TCSS 变量文件

Textual 的 TCSS 是 CSS 子集且有原生主题变量系统，本文档的 token 可近乎 1:1 写成变量文件，**Web 端与终端端共用同一份设计语言、同一套命名**。

```tcss
# pto.tcss —— 由本文档直接生成
$background: #101010;      $surface-1: #161616;
$surface-2: #1c1c1c;       $surface-3: #262626;
$foreground: #e8e8e8;      # .90 预合成
$foreground-secondary: #a4a4a4;
$foreground-muted: #777777;
$primary: #0077ff;         $success: #04d793;
$warning: #ffaa3b;         $danger: #ff4b7b;

KernelTable {
    background: $surface-1;
    border: round $surface-3;   # radius-lg → ╭╮╰╯
    padding: 1 2;               # space-4 → 1 row / 2 col
}
KernelTable > .row--selected { background: #18293c; }  # state-selected
```

### 组件评审门槛（继承 PTO preview-gate 流程）

每个组件实现时必须声明：**所属渲染层（T0–T4）· 降级路径 · 键盘等价操作 · 使用的 PTO token**。
**禁止在业务模块里直接造新样式**——需要新样式先做 preview 页确认没有可用组件，再加入 `pto.tcss`。

## 7. 粒子 / 像素 / 游戏化点缀 — 允许在哪、禁止在哪

PTO 的设计定位是「技术、克制、精确」，且明确规定「动效只服务于功能，无装饰性循环动画」。粒子与像素风格看似与之冲突——**解法不是折中，而是划清边界：装饰只能出现在没有数据的地方。**

### 允许的四类时刻

| 时刻 | 手法 | 理由 |
|---|---|---|
| **启动 splash** | 像素字 Logo + 低亮度粒子场（方形点，非圆点）+ 字符雨 | 此刻屏幕上没有任何需要精读的数据；且这是唯一一次给产品做性格表达的机会 |
| **空态 / 等待** | 极简像素动画（≤4 帧循环），仅在真实 pending 时 | 填补空白优于留白发呆，但不能常驻 |
| **里程碑达成** | 成就徽章（`▪ 零配置启动` `▪ 改动有证据`）| 长任务收尾时给一次正反馈，帮助建立"这一轮真的完成了"的心理终点 |
| **章节过渡 / 演示模式** | 扫描线、像素编号、发光计分板 | 演示与评审场景，不是日常工作态 |

### 禁止的场合（无例外）

- **任何数据可视化区域**——热力图、Trace、曲线、gauge 上不加任何装饰效果
- **审查与决策界面**——diff、Evidence、Approval 是最需要冷静的地方
- **常驻界面元素**——底栏、Dock、面板边框不做发光/呼吸/渐变
- **告警与错误态**——危险信息靠语义色和字形，不靠特效放大

### 具体实现纪律

```
粒子：方形像素点（fillRect 而非 arc），品牌蓝占比 ≤ 30%，
      单点 alpha ≤ 0.4，下落速度 ≤ 0.25px/frame
像素字：仅用于 Logo 与数字（成就计数、Act 编号），正文永不像素化
发光：text-shadow 半径 ≤ 14px，仅用于品牌色数字与 Logo
扫描线：opacity ≤ 0.35，行距 3px，静止不动（滚动的扫描线会引起眼疲劳）
成就徽章：方形指示块（8×8，radius 1px）+ 文字，不用 emoji、不用奖杯图标
```

### 实拍验证的三个具体做法

| 做法 | 出处 | 说明 |
|---|---|---|
| **描边块字 Logo** | Rebels in the Sky · term-rex | 块字符主体 + 单像素描边/投影，比纯 `██` 立体得多；仅用于 splash |
| **反色键位 chip** | Rebels in the Sky 底栏 | 按键用反色小块 <code> Esc </code> <code> ↵ </code>，动作用常规文字——比纯文本 keybar 易扫读一个量级，且不占额外行 |
| **像素图标** | term-rex 恐龙 · Rebels 地球 | 用块字符 + 半块拼 8-bit 图形，配色控制在 3–4 色内 |

这三条都落在"装饰只在无数据处"的边界内：Logo 与像素图只出现在 splash，反色键位 chip 属于 Chrome 层的常驻组件（它承载的是操作提示而非数据）。

### 视觉流派定位（详见 ../web/visual-analysis.html）

TUI 世界有五个可辨识的审美流派，DevKit 的定位是**主体站技术克制派，按场景向外逐级放开浓度**：

```
宣传页 ─▸ Splash ─▸ 空态/成就 ─▸ 工作台常态 ─▸ 审查/诊断
渐变辉光   磷光扫描线   反色标签      中性6级+单强调    只有语义色
粒子像素   描边块字·2秒  点阵分隔线                      最克制
◀────────────── 浓度递减 ──────────────▶
```

| 流派 | 代表 | 取舍 |
|---|---|---|
| 技术克制 | PTO · Warp · Resend · Cursor | **主位置** |
| 粗野荧光 | AwesomeTUI | 借手法不借浓度，用于 splash / 宣传 |
| 糖果友好 | Charm 全家桶 | **视觉不借**（吉祥物与糖果色削弱工程可信度），API 深度参考 |
| 复古磷光 | cool-retro-term | 限 splash 2 秒 |
| 霓虹赛博 | Puku CLI · Tokyo Night 系 | 仅演示过场（太流行反而无记忆点） |

**一句话定位**：视觉人格是「一台精密仪器，而不是一张海报」——启动那两秒可以有性格，工作的几小时里必须退到背景里。

### 外部视觉参考：AwesomeTUI 的手法

`awesometui.com` 的站点视觉是"终端美学"在 Web 上的一次高完成度表达，其**手法**值得借鉴（注意：借手法，不借色板——我们的品牌色是 `#0077FF`，它用的是荧光青柠）。

| 手法 | 做法 | 我们能用在哪 |
|---|---|---|
| **抖动像素排版** | 标题字用点阵抖动做边缘，形成"半像素化"质感，而非纯方块 | splash 的 DevKit 字标；成就徽章数字 |
| **单一荧光强调色** | 全站只有黑 + 一个荧光色 + 白，强调色浓度极高所以每次出现都有分量 | 提醒我们：品牌色**出现频率越低越有力**，不要满屏蓝 |
| **点阵尘埃图形** | 世界地图由散落方点拼成，密度渐变 | 已用于报告 hero 粒子场；splash 可用同法做鲲鹏芯片轮廓 |
| **角部裁切标记** | 四角 `+` 十字标 + 细外框，像技术制图/印刷套准线 | 演示模式的画面边界；导出报告的页角 |
| **反色分段标签** | logo 做成 `>` ▸ `AWESOME`(反色) ▸ `TUI`(正色) 三段拼接 | 已用于 keybar 键位 chip；可扩展到状态徽章 |
| **点阵分隔线** | 分隔线用方点而非实线 | 次级分组分隔，比实线轻、比留白明确 |
| **大字号等宽标题** | 正文级 mono 放大到 display 尺寸做主张 | 报告与 splash 的标语行 |

**不借的部分**：它的荧光色浓度适合宣传页，不适合长时间盯着看的工作台；它几乎没有中性层级（只有黑白 + 荧光），而我们需要 6 级表面来承载密集信息。**宣传物料可以更浓，产品界面必须回到 PTO 的克制。**

### 强调色配额 — 蓝出现得越少越有力 ⭐

第一版把蓝铺得太开：区块标题的 `#` 前缀、面板的 `>_` 提示符、状态栏首段、筛选按钮激活态、置信度与兼容度进度条、splash 字标的一半、粒子场的三成粒子——全是品牌蓝。结果是**蓝不再指向任何东西**。当一屏有十几处蓝，工程师就无法靠余光找到"我现在在哪、下一步点哪"，强调色退化成了背景纹理。

这正是 AwesomeTUI 那条观察的反面教材：它全站只有黑 + 一个荧光色 + 白，**强调色浓度极高所以每次出现都有分量**。我们抄了它的手法，却没抄它的克制。

所以给蓝定一条配额规则：

> **蓝 = 当前对象，或当前唯一推荐的动作。** 除此之外一律中性。

按这条把每一处蓝重新过了一遍：

| 承载点 | 判定 | 处置 |
|---|---|---|
| Dock 选中项（整行同色 + 左竖条） | 当前对象 | **保留** |
| 激活 tab 的顶部实心条 | 当前对象 | **保留** |
| 运行中任务的 `▶` 图标 | 当前对象 | **保留** |
| 输入提示符 `❯` 与光标 | 当前动作入口 | **保留** |
| `[Y] 应用方案 A` / `[A] Accept` / `▸ [1] 下一步` | 当前唯一推荐动作 | **保留**（一屏一个） |
| 区块标题 `#` 前缀 | 常驻装饰，不是状态 | → 中性 `fg4` |
| 面板提示符 `>_` | 常驻装饰（一屏 2–3 个） | → 中性 `fg4` |
| 状态栏首段实心蓝 | 常驻且面积大 | → 中性反色，**靠明度分段而非色相** |
| 筛选/排序按钮激活态 | 筛选器不是当前对象 | → 提高明度（`fg` + `fg3` 描边），不用色相 |
| 标签流激活态 | 同上 | → 同上 |
| 置信度 / 兼容度进度条 | **数据可视化** | → 中性，**数值本身承担强调** |
| `AUTO` 状态徽章 | 是模式不是严重度 | → 中性反色；红/琥珀/绿留给真正的语义档 |
| 证据行的 `↵` 跳转标记（一屏 3 个） | 可用性提示 | → 中性 `fg4` |
| splash 字标的 `KIT` 半边 | 静态标识 | → 中性灰（白 + 灰两色分段，呼应标识的红 + 灰） |
| splash 抖动衰减带 | 装饰 | → 中性灰阶 |
| splash 光晕 | 装饰（且把 Kunpeng 红标罩上了蓝 halo） | → 字标白光晕、标识红光晕 |
| 粒子场蓝粒子占比 28% | 装饰 | → 8% |

改完之后，一屏典型工作台上的蓝**从十几处降到 4–5 处**，且每一处都能回答"它指向什么"。splash 更极端：整屏唯一的彩色是 Kunpeng 红标，字标白灰、徽标中性、抖动灰阶——**红做身份，蓝做交互，两者在 splash 上不打架，因为 splash 没有交互态。**

配套的一条判据，供后续评审用：**遮住屏幕上所有蓝色，还能不能说清"我现在选中的是什么"？** 能，说明蓝铺多了（信息已经被别的编码承担）；完全说不清，说明蓝用对了地方。

### Kunpeng 标识与身份色 — 红只做身份，不做界面 ⭐

产品名是 **Kunpeng DevKit AI**，标识是鲲鹏的红灰飞鸟/箭矢。鲲鹏视觉体系承袭华为品牌色系：**华为红 `#ED1C24` + 科技黑 `#000000` + 纯净白 `#FFFFFF`**。（说明：手上这份标识资产实测取色是 `#C7000B`，比品牌红更深；我们统一按品牌规范的 `#ED1C24` 渲染，并在生成标识位图时做了整体校色。）

这就带来一个必须先解决的冲突：**红在 TUI 里已经被占用了**。编译失败、Critical 兼容性问题、进程崩溃——这些都是红。如果品牌红同时是界面强调色，工程师就无法在余光里区分"这是鲲鹏的产品"和"这条构建挂了"。而在终端里，余光判断正是最高频的动作。

所以定死一条硬规则：

| 颜色 | 职责 | 允许出现的地方 | 明确禁止 |
|---|---|---|---|
| **Kunpeng 红 `#ED1C24`** | **身份** | splash 字标、顶栏迷你标识、`NEW` 新增标 | 强调色 / 选中态 / 焦点 / 链接 / 语义色 / 任何数据可视化 |
| **品牌蓝 `#0077FF`** | **交互** | 选中、焦点、当前对象、可点击、进度、主按钮 | 表达"失败"或"新增" |
| **错误红 `#FF4B7B`** | **语义** | 失败、Critical、删除行 | 品牌表达 |

判据很朴素：**看到红色时，我该想到"华为鲲鹏"还是"出事了"？** 只要一屏里两种含义同时出现，这条规则就已经被违反了。因此红的出现次数被压到极低——常态工作台里只有顶栏那一枚 26px 标识是红的，其余全屏无红，红一出现要么是标识要么是真出问题。

这条其实和鲲鹏 DevKit 社区站的用法一致：社区站通篇白灰黑，红只出现在三处——站点标识、当前导航项及其下划线、`New` 徽章。**红在那里也是"归属 + 新增"，不是"强调"。** 我们把这套原样搬过来，只是把"当前导航项"这一处让给了蓝——因为社区站没有失败态，我们有。

社区站另外两点直接对得上我们已有的方向：卡片是**纯色底 + 1px 细边 + 极小圆角**的方形（对应上一节的"方形"），主 CTA 是**黑色实心 + 次级描边**的双层按钮（在暗色下反过来：主按钮走亮底反色，次级走描边）。

**`NEW` 标**是从社区站借的第三件东西：小尺寸、方形、红底白字、全大写紧字距（`.new`）。它是红被允许的唯一"功能位"——因为"新增"和"失败"不会在同一个语义槽里争。

但它**不进常态 Chrome**。曾经把它挂在顶栏的 `DEVKIT AI` 后面，试过就撤了：顶栏是全程常驻的，一个永远亮着的 `NEW` 既失去了"新"的时效意义，又让本该只有一处红（标识）的顶栏出现第二处红，两块红互相削弱。`NEW` 只开放给**列表项**（`ITEM({nw:1})`），用于标注刚上线、用户可能还没用过的能力——它必须是会消失的，否则就不是徽章而是装饰。

于是顶栏的最终形态是：**Kunpeng 标识（唯一的红）+ `KUNPENG`（中性描边）+ `DEVKIT AI`（中性反色）+ 闪烁块光标 + 版本号**。整条顶栏只有一处彩色。

### 启动页：先问一句"这在终端里画得出来吗" ⭐

第一版启动页不成立。它有三处终端根本做不到的事：**字标带高斯模糊光晕**（`text-shadow: 0 0 16px`——终端只有字符和颜色，没有模糊）、**元素自由定位**（图形和文字各自居中，不落在同一套字符网格上）、**背景是 canvas 粒子**（亚像素运动的圆点，终端画不出来）。做出来像一张 Web hero 配图，不像一个 TUI 工具起来的第一屏。

重做时定的判据只有一条：**这一屏的每一个像素，都必须是某个字符格里的某个字符。** 由此得出四条：

**① 字标改成 5 行块字体，写全名。** 之前只有 `DEVKIT` 是块字，`KUNPENG` 是一行小字距标签——名字被拆成了两个层级。现在 `KUNPENG DEVKIT AI` 整体用同一套 5 行点阵字体拼出来，**且整条统一走白**。中间试过把 `KUNPENG` 压成灰、`DEVKIT AI` 留白，想用明度区分归属与主体——但那等于又把名字拆回两个层级，而且灰字标在暗底上整体发闷。产品名是一个整体，`KUNPENG` 不是它的前缀修饰。归属与主体的区分留给顶栏的分段标识（`KUNPENG` 中性描边 / `DEVKIT AI` 中性反色），启动页不重复表达。字宽 5 列 + 1 列间隔，93 列——在 156 列的终端里放得下，和左边 26 列的标识并排是 121 列，还留有余量。

**② 辉光只用 bloom，不用字符环。** 曾经试过一版"用字符做辉光"：背景字符场在字标外侧生成一圈抖动环，理论上很动听——终端做不出模糊但做得出密度，远看发光、近看每格都是 `+`。**实际做出来是灰蒙蒙的一片，读起来是"脏"不是"亮"。** 原因不难理解：辉光靠的是**连续的低强度光**，而字符场只能给出离散的中等强度点；密度再低，每个字符仍是一个有明确边界的实体，一堆实体挤在字标周围就是噪点，不是光。

所以撤了，辉光交给 bloom（大半径低透明度的 text-shadow），字符场只负责四周的质感、字标周围保持干净。**这是"字符能表达一切"这条信念的一个边界**——密度能替代明度做层级、能替代色阶做热力，但替代不了辉光。

**bloom 的一个坑**：第一版给字标加了 `0 0 2px` 的紧贴白影，结果块字体的直角边缘被糊掉，点阵感全没了。辉光只能用大半径低透明度的层（12px / 34px / 70px），**不能有小半径层**——否则就是在给像素字体做抗锯齿，把它最重要的特征抹掉。

**②.4 流光是真的在动，字符逐帧换。** 第一版拿 `background-position` 位移了一条渐变亮带——字符不动只有颜色缓慢推移，结果是"渐变呼吸"，不是流光，被当场否掉。

第二版把它做成了真动效——但做成了**全屏横扫**，一整道光带从左扫到右，太抢戏。启动页的主角是产品名和 boot log，背景动效的职责是"让画面活着"，不是让人去看它。

第三版收到角落，但做成了同心波——规整的环形太"机械"，像雷达扫描。

第四版做成十团游离光斑，还是不对——团太大、动得太慢，看着"重"。

**最终版是四周一圈细碎的明灭光点**：几十个小光点在点阵外圈随机点亮又熄灭，每颗只占 1–5 格（三成带一圈晕），寿命 0.3–1.2s，熄灭后立刻在外圈另一个位置重生。位置从**预筛出的"外圈可点亮格子"列表**里随机取——所以光点天然只出现在有料的地方，且四周（含上下）均匀分布。帧率提到 ~33fps，明灭才利落。

**参数的方向感**：小、快、多、随机 —— 这四条一起才叫"灵动"。大而慢的光斑无论怎么调亮度都是"重"的；把单体缩到几格、寿命压到一秒内、数量提到几十个之后，同样的总亮度读起来就完全不同了。

**底图也跟着改细**：字符梯度里去掉了 `░ ▒` 这类成块的字符，只留 `· - +`；团块噪声尺度从 13/4.5 收到 6.5/2.4。之前那版的"块感"来自这两处，不是来自光。

**这才是终端做得出的动效**：同一批单元格，逐帧重新写入不同的字符和颜色——正是 TUI 每帧在做的事。相比之下，位移一整块渐变在终端里没有对应操作。帧率压到 ~24fps（`ts-last<42` 直接跳过），和终端全屏重绘的量级对齐；离开启动页时 `stopFlow()` 立刻停掉 rAF——**工作台常态一帧装饰动画都不跑**，这是 §5 Motion 那条纪律的边界。

**给动效划范围，比调动效参数更管用。** 全屏横扫时我花了好几轮去调带宽、亮度、密度门限，本质上是在找"既看得见又不烦人"的那个平衡点——而这个点不存在，因为横穿全屏这件事本身就在抢注意力。范围一收到角落，亮度反而可以给足，因为它已经不在视线主路径上了。

**②.45 密度要长成团块，不能是同心环。** 第一版的密度只有一个径向渐变，结果四周是一圈均匀的环，很假。现在叠了两级值噪声（低频 13 格 + 中频 4.5 格，双线性插值），密度长出不规则的连续团块——形态上更接近半调点阵地图那一类参照物，也更像"有东西在那里"而不是"有个渐变在那里"。噪声用确定性哈希，重绘不会跳。

**②.5 背景加了空间渐变。** 参考彩色 ASCII 艺术的做法——同一片字符，颜色沿空间连续过渡。字符场用 `background-clip: text` 上一层 148° 线性渐变（钢蓝 → 墨绿 → 钢蓝，全部低饱和且极暗），两层光点各自也走同一角度的渐变，只是明度更高。**渐变和半调是同一套字符在承担**：颜色连续变化，载体始终是离散的字符格。饱和度压得很低是刻意的——参考图那种荧光青绿适合做单张海报，不适合当一个每天要盯着的工作台的开场。这样"渐变"和"半调"是同一套字符在承担：颜色连续变化，但载体始终是离散的字符格。（曾经还叠过一层径向渐变去提亮字标周围，和上面那圈字符环一起撤了——同一个原因。）

**③ 背景是字符半调场，不是图片。** 参考 GitHub 官网那种半调点阵渐变和 TUI Studio 的 ASCII 场：中心留白保证内容干净，向外用 `· - + ░ ▒` 逐级加密。密度函数是一个椭圆距离场加确定性哈希噪声（**不用 `Math.random`**——否则每次重绘背景都在抖）。整场颜色压到 `#232323`，只做质感不抢内容。字符网格按终端真实尺寸实时算，改字号它自己重排。

**④ 加一段 boot log。** 真正的 TUI 起来时会打一串带时间戳的启动记录，这既是行业惯例也是有效信息。现在首屏有五行 `[ 0.004] ok runtime …`，把"本地已就绪 / 交叉编译目标 / MCP 工具装载 / 3 项能力未安装 / 恢复上次会话"一次说完——**它同时承担了 Landing 四要素里的环境状态、阻塞项和可继续上下文**，比原来那几行散装提示信息密度高得多，也更像这个品类该有的样子。

这条判据值得复用到所有视觉提案上：**先问"终端画得出来吗"，画不出来的效果再好看也不要**——否则设计稿和实现之间会留一道永远填不平的沟。

### 输入框归属会话，不归属窗口

输入框原来是一条横贯终端全宽的带子，压在 Dock 下面。评审时被问："输入应该在页面下面吗？一个页签对应一个？"——后半句正是答案：**输入属于当前这个会话，不属于这扇窗口**。

一个页签就是一个任务会话，有自己的上下文、自己的对话历史、自己的输入。窗口里可以同时开着"migrate nginx"和"param tuning"两个会话，它们各自的输入互不相干。所以输入框应该在**主区内**、与 tab 同列，而不是跨到 Dock 底下——跨过去等于在说"这个输入是全窗口的"。

留在全宽的只有两条：**keybar**（当前上下文可用的键，随幕变化）和**状态栏**（workspace / 模式 / 模型 / 上下文水位，全局唯一）。判据很简单：**切换页签会变的东西，归页签；不变的，归窗口。**

### Shell 结构：左栏要从顶通到底

原来的结构是「全宽 appbar → 下面才分左右」，评审时被指出"结构不太好看"，看图确实如此：appbar 是一条横贯全宽的带子，内容只有最左的品牌和最右的状态，**中间一大段是空的**；而它下面的 tab 带又从 Dock 的右边缘才开始。于是屏幕上出现两条起点不同的横向分割，左上角那块区域归属不明——它既不属于 Dock，也不属于主区。

改法是把左栏提到顶：**Dock 从标题栏下方一直通到状态栏**，品牌标识进 Dock 的头部；tab 带缩回主区，并把原来 appbar 右侧的状态 chip 和版本号并进 tab 带的右端。结果是一条垂直分割贯穿全屏，一条水平分割横贯全屏，**两条线各只出现一次**。这也正是 MobaXterm / VS Code / Zed 一类工作台的通行结构——侧栏是第一级划分，标签页从属于内容区而不是从属于窗口。

顺带省下一整行高度（原来 appbar 44px + tabs 44px 两条带，现在合成一条），在 1080p 下这行高度直接给了画布。

一个细节：Dock 头和 tab 带**必须等高**，否则那条水平分割线会在中间断一截。两边都写死同一个高度值（1080p 下 50px），不靠内容撑。

### 输入框：全场最高频的交互面，必须是真组件

工作台的输入行原来是一行裸提示符 `❯ ` 加光标——这正是之前那条"Chrome 层要用真组件"的漏网之鱼，而且漏得最不该：**它是全场使用频率最高的交互面**，十幕里每一幕都在。

现在它是一个真输入框：描边 + 2px 品牌色焦点环 + 占位提示（"描述你想做什么，或用 / 调命令"）+ 右侧快捷键槽（`Ctrl+P` 命令面板）。启动页那个是它的放大版——820px 宽、焦点环更明显、占位符给了具体例句（"把 ./nginx 迁到鲲鹏"），因为首屏的输入框还要承担**教用户怎么说话**的职责，下方那排建议 chip 是同一个目的。

一个小细节：光标要放在占位符**前面**。真实输入框的插入点在位置 0，占位符是它右边的灰字；把光标放在占位符尾巴上，看着像用户已经输入了那段文字。

### 标识的两个渲染档位

同一枚标识按终端能力分两档渲染，对应 TUI-CAPABILITY.md 的渲染分层：

**T5 · 光栅**——终端支持图形协议（Kitty / Sixel / iTerm2）时，直接把标识位图画进单元格网格。顶栏用这一档：26×26 的标识在 3 行高度里必须清晰，半块字符做不到。

**T1 · 半块像素**——纯字符降级。每个字符格承载 **2 个垂直像素**（`▀` 上半、`▄` 下半、`█` 双满、前景色配背景色可在一格里表达两种颜色），把标识重采样成 36×13 字符 = 36×26 像素。splash 用这一档——**它不只是降级，也正是我们要的像素调性**：字标本身就是点阵抖动的，标识做成同样的像素颗粒，两者是一套语言。

半块技法的价值不止于此：它把终端的**垂直分辨率翻倍**，是 T1 层最高性价比的一招，同样适用于稀疏火焰图、小尺寸 sparkline。

### 落到 demo 的四条：文字底色 / 字体 / 颜色层级 / 方形

上表是"能借什么"，这四条是**已经落进 `../web/demo.html` 的执行规则**——它们是手法层，叠在 PTO token 之上，不改 token 本身。

**① 文字底色（反色分段）**——不用边框、不用色块背板，直接给文字上底色，靠底色本身划分层级。落地三处：应用标识做成 `DEVKIT`(品牌底 + 深字) ▸ `AI`(surface-4 底 + 亮字) ▸ 闪烁块光标三段拼接；`AGENT CONSOLE` 这类小节标签由灰字改成反色块（`.ivl`，另有 ok/warn/error 四色变体）；状态栏首段由半透明品牌色改成实心品牌底 + 深字。规则是**一屏最多三处反色**，超过就失去分段作用。

**② 字体（靠字距而非字号建层级）**——终端只有一级字号，Web 侧模拟时也刻意不靠字号拉开差距。区块标题一律 mono + 全大写 + `letter-spacing .20–.22em`，正文保持 `.01em`。这样 8.5px 的 `# TASKS` 和 11.5px 的正文行仍有清晰主次。**注意 CJK 标题不做全大写**（无大小写形态），只保留字距。

**③ 颜色层级（整行同色，不只染标签）**——AwesomeTUI 的分类列表里，激活项的 `#` 前缀、标签、右对齐计数**一起**变强调色。我们据此改了选中态：`.item.sel` 下的 `.idx / .ico / .lb / .meta` 全部转 `--pri-h`，左侧 2px 实心品牌竖条贴边（不再留缝、不再圆角）。对照面：排序按钮激活态**只上描边和文字色、不填充**（`.sbtn.on`），因为它是筛选器不是当前对象——**"我是谁"用实心，"我选了什么"用描边**。

**④ 方形（直角作为默认，圆角作为例外）**——原先的圆角是 Web 习惯的残留，与终端的字符网格冲突。全量收敛：列表项 / tab / diff token / 进度条 → `0`；chip、pill、按钮、徽章 → `2px`（保留一丝亚像素柔化，避免锯齿感）；只有**真正浮起的东西**保留可见圆角——终端外框 `5px`、模态浮层 `4px`。这正好复用了 §4 的 Radius 两档规则：**圆角 = 浮起**，其余一律直角。

**配套的两个新组件**：`.sortg/.sbtn` 排序筛选按钮组（方形描边 + 图标 + 计数，激活态描边上色）与 `.tagf/.tg` 标签流（`#TAG` + 右侧计数，流式换行）。两者都来自 AwesomeTUI 的 `/system` 页面，填补了我们此前"筛选与标签"没有组件形态、只能用文字凑的空缺。

**splash 字标**同步改为两色分段（`DEV` 白 / `KIT` 品牌蓝）+ 三行像素抖动衰减带，对应上表的"抖动像素排版"；抖动只出现在 splash，工作台常态零装饰（见 §7 浓度梯度）。

### 状态徽章：反色 chip + 色轨（源自 Specify CLI 实拍）

Specify CLI 的输出把状态做成**行首反色徽章 + 左侧色轨**，而不是整行染色：

```
┃ FAILED    Personal access token missing
┃ SUCCEEDED Pulled rules from repository @specify/all-tokens
┃ WARNING   Trial expires in 30 days
```

这正好兑现我们那条"语义色只上字符与短标签，不上整行文本"的纪律——**徽章承载状态，正文保持中性**，长日志里也不会变成一片彩色噪音。已用于 Agent Console 的构建输出。

### 在终端里怎么落地

TUI 无法做真正的粒子系统，但可以：
- **启动 splash**：块字符 Logo（见 JOURNEY.md 的 Landing 屏）+ 稀疏 braille 点阵渐显，2 秒内结束
- **成就徽章**：`▪ 零配置启动` 这类方块前缀 + 文本，用 success 色
- **像素数字**：大号统计数字用块字符拼（如 Session Summary 里的关键指标）

> **一句话原则**：装饰服务于「这是什么产品」的性格表达，数据服务于「现在发生了什么」的判断。两者<b>在空间上永不重叠</b>——这条比任何具体参数都重要。
